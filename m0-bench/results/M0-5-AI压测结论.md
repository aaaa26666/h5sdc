# M0-5 结论：AI 寻路与同屏数量压测

- 任务编号：M0-5
- 测试台：`m0-bench`（`scenes/ai/`）
- 引擎：Three.js 0.186.1
- 目标机：i5-13600KF / RTX 3060 / 32GB / Windows 11 / Chrome 153
- 原始数据：`results/raw-ai-sweep.json`、`results/raw-ai-pf.json`、`results/sweep-log.txt`、`results/pf-log.txt`
- 计时器分辨率：**0.005 ms**（已通过跨源隔离恢复；未恢复时为 0.1ms，会导致 AI 成本全部量成 0）

---

## 1. 单次操作成本（批量微基准，权威数据）

| 操作 | 单次成本 | 备注 |
|---|---|---|
| A* 单次查询 | **0.0184 ms** | 48×48 网格，八向，禁止穿角，平均路径 25.5 格 |
| 流场单次全图重算 | **0.0718 ms** | 2304 格全覆盖，**与 Agent 数量无关** |
| 视线检测单次射线 | **0.000093 ms** | 93 纳秒，网格 DDA，射程 24 世界单位 |

> 微基准采用"批量执行 N 次再相除"，不受 `performance.now()` 分辨率限制。
> per-frame 累加计时只能作为交叉验证，不能作为结论依据。

## 2. 每帧成本构成（按 Agent 数量，中位数）

### CPU 节流 1x（本机全速）

| Agent 数 | 帧 CPU P95 | 渲染 P95 | AI 合计* | AI 占比 | 寻路最坏帧 |
|---|---|---|---|---|---|
| 50 | 1.61 ms | 1.58 ms | 0.04 ms | 2.4% | 1.96 ms |
| 100 | 2.18 ms | 2.11 ms | 0.07 ms | 3.1% | 3.00 ms |
| 200 | 2.61 ms | 2.45 ms | 0.16 ms | 6.1% | 5.66 ms |
| 300 | 3.05 ms | 2.82 ms | 0.23 ms | 7.6% | 8.17 ms |
| 400 | 3.28 ms | 2.99 ms | 0.29 ms | 8.9% | 9.68 ms |

\* AI 合计 = 帧 CPU − 渲染，即寻路 + 视线 + 移动

### CPU 节流 6x（模拟低端 CPU）

| Agent 数 | 帧 CPU P95 | 渲染 P95 | 寻路最坏帧（A*） | 寻路最坏帧（流场） |
|---|---|---|---|---|
| 50 | 16.84 ms | 16.19 ms | 9.46 ms | — |
| 100 | 21.67 ms | 20.59 ms | 21.44 ms | — |
| 200 | 24.24 ms | 20.53 ms | **44.95 ms** | **2.01 ms** |
| 400 | 22.55 ms | 18.06 ms | **68.29 ms** | **2.38 ms** |

---

## 3. 结论

### 结论 1：AI 寻路与视线检测不是瓶颈，渲染才是
在 N=400、全速下，AI 总成本 0.29ms，占帧 CPU 的 8.9%；剩余 91% 是渲染。
即使 6x 节流，AI 占比仍不到 10%。**把优化预算投在 AI 上是投错了地方。**

### 结论 2：视线检测不需要降频，可以每帧全量做
单次 93ns。400 个 Agent **每帧全部**做视线检测 = 0.037ms，相对 16.67ms 预算可忽略。
原设计里"按 losMs 错峰检测"属于过度优化，M1 可直接简化为每帧检测，代价是逻辑更简单、响应更及时。

### 结论 3（最重要）：A* 的尖峰是致命风险，必须做查询预算限流
当 N 个 AI 被同一事件（枪声、警报、玩家暴露）同时触发重规划时：

| 方案 | N=200 最坏帧 | N=400 最坏帧 | 后果 |
|---|---|---|---|
| 每 Agent 独立 A* | 44.95 ms | **68.29 ms** | 单帧卡死 1~4 帧，60fps 下为可见冻结 |
| 共享流场 | 2.01 ms | **2.38 ms** | 无可见影响 |

差距 **20~30 倍**。这是本项目 AI 架构的第一个硬约束。

### 结论 4：关卡墙体的渲染成本远超 AI
约 312 个独立墙体 Mesh 在 6x 节流下约占 15ms/帧，是 AI 成本的数十倍。
**M1 起关卡几何必须走实例化/合批**，否则低端机预算会被静态场景吃光。

---

## 4. 对 M1 的架构约束（建议写入《技术选型结论》）

1. **分层寻路**：常态移动用共享流场或共享路径；个体独立 A* 仅用于少数精英 AI。
2. **寻路查询必须限流**：任何情况下禁止 N 个 Agent 在同一帧无限制发起 A* 查询。
   必须实现每帧查询预算（排队处理），单帧寻路耗时上限设为 2ms。
3. **视线检测每帧全量**，不做错峰（成本可忽略，简化逻辑并提升响应）。
4. **关卡静态几何必须实例化/合批**，与 AI 无关，但是更大的预算项。
5. **同屏 AI 数量上限**：本机全速下 N=400 时 AI 仍不是瓶颈；
   真实上限由渲染决定，需在 M7（正式美术资源）与 M8（优化）后重新测定。
   **当前不建议写死某个数字**，因为渲染基线还会变。

---

## 5. 本结论的已知局限（必须随结论一并引用）

1. **6x CPU 节流只模拟慢 CPU，不模拟慢 GPU**。真实低端机的 GPU 更弱，渲染成本会高于本文数字。
2. **渲染数字是"未优化逐 Mesh 基线"**：墙体与 Agent 全部使用独立 Mesh，未使用实例化、LOD、遮挡剔除。
   该数字代表"最差实现"，不代表最终成本。
3. **`--vsync off` 下 frameP95 受帧队列流水线影响**，与 avgFps 不自洽
   （出现过 frameP95=30ms 但 avgFps=74 的情况）。因此**判定以 `cpuP95` 为准**，`frameP95` 仅作参考。
4. **AI 行为极简**：本压测只含寻路、视线、直线移动，不含动画、射击、状态机、感知记忆。
   加入这些后 AI 成本会上升，但按当前占比（<10%）推算，仍不太可能成为主要瓶颈。
5. 本次扫描第一次遗漏了 `--pf` 维度（跑的全是 A*），已补测；
   完整数据见两份 log，未补测的组合不得据本文推断。
