# M0-7 结论：音频自动播放限制验证

- 任务编号：M0-7
- 探针：`m0-bench/scenes/audio/`（`harness/audio.mjs` 驱动）
- 测试浏览器：Chrome 153.0.8010.53、Edge 136.0.3240.92
- 原始数据：`results/audio-log.txt`、`results/audio-probe-*.json`
- 计时器：已开跨源隔离，`performance.now()` 分辨率 5µs

---

## 1. 实测结果

| 项 | Chrome · 默认策略 | Edge · 默认策略 | Chrome · 放宽策略 | Edge · 放宽策略 |
|---|---|---|---|---|
| AudioContext 初始 state | **suspended** | **suspended** | running | running |
| AudioContext 创建耗时 | 29.92 ms | 43.22 ms | 25.69 ms | 39.11 ms |
| `ctx.resume()` 无手势 | **永不 settle** | **永不 settle** | resolved | resolved |
| `<audio>.play()` 无手势 | **NotAllowedError** | **NotAllowedError** | played | played |
| 手势后 `ctx.state` | running | running | running | running |
| 手势后 `<audio>.play()` | played | played | played | played |
| 解锁总耗时 | **15.69 ms** | **25.39 ms** | 1.06 ms | 1.83 ms |
| 解码 30s 立体声 WAV | 60.44 ms | 59.07 ms | 59.38 ms | 50.35 ms |

音频参数（两浏览器一致）：`sampleRate 48000 Hz`、`baseLatency 0.01`（10 ms）、`outputLatency` 报 0。

格式支持（Chrome / Edge 均返回 `probably`）：
MP3、AAC(mp4a.40.2)、OGG Vorbis、OGG Opus、WebM Opus、FLAC、WAV(PCM) —— **全部支持**。

---

## 2. 结论

### 结论 1（最关键的坑）：无手势时 `ctx.resume()` **永不 settle**

它既不 resolve 也不 reject，promise 永久挂起。

**后果**：若代码在加载流程里写 `await audioCtx.resume()`，**整个加载流程会永久卡住、不报错、不超时**。
这是最难排查的一类缺陷 —— 没有异常、没有日志，只有卡死。

**必须遵守的约束**：任何 `resume()` 调用都不允许被 `await` 在加载/初始化路径上。
只允许两种形态：
- 在用户手势回调里 `resume()`（可 await，此时必 settle）
- 若真要提前尝试，必须用 `Promise.race` 加超时兜底，且超时后按"未解锁"分支继续

### 结论 2：`<audio>.play()` 无手势时抛 `NotAllowedError`
错误名可用于判定"被拦截"与"其他错误"，实现精确的降级分支。

### 结论 3：解锁成本很低（15.7~25.4 ms），一次性
放在"点击开始"那一次手势里完成，玩家完全无感。**不需要为此做复杂的预加载策略。**

### 结论 4：AudioContext 创建要 25.7~43.2 ms，不应放在首屏关键路径
相对于 106.7 KB 的 JS 首包与 6 秒进图预算，40ms 不算大，但它是**同步阻塞**的。
应在大厅空闲时或首次手势时创建，不要塞进进图加载的关键路径。

### 结论 5：解码成本可测可控
30 秒立体声 WAV（5.17 MB 未压缩 PCM）解码 **50~60 ms**。
**注意**：这测的是 PCM 解码。真实游戏用压缩格式（MP3/Opus/AAC），解码成本与之不同，**不得据此推断**。

### 结论 6：Chrome 与 Edge 行为完全一致
两者同为 Chromium 内核，本次全部项目结论一致，Edge 可直接沿用 Chrome 的结论。

## 3. 对 M1 的方案约束（建议写入《技术选型结论》）

**必须实现"音频解锁门（Audio Unlock Gate）"**：

1. 游戏入口第一个可交互界面上放一次明确的点击（如"点击开始"），
   在该手势回调内**一次性**完成：创建 AudioContext → `await resume()` → 播放一次静音音频占位。
2. **禁止**在任何模块顶层或加载流程中 `await ctx.resume()`。
3. 未解锁前，所有音频播放请求走"静默丢弃 + 排队"分支，不得抛异常中断游戏逻辑。
4. 若检测到 `promise` 在 N ms 内未 settle，按未解锁降级处理，**不得阻塞流程**。
5. 音频格式：Chrome/Edge 全格式支持，可按压缩率自由选择（推荐 Opus，压缩率最优）。
6. AudioContext 创建放在手势回调或大厅空闲期，**不放入进图关键路径**。

## 4. 本结论的已知局限

1. **只测了 Chromium 系（Chrome 153 / Edge 136）**。Firefox 未安装 → **未测**；
   Safari 未测。《流程文档》9.4 兼容矩阵要求覆盖 Firefox 与 Safari，
   **该项在 M0 未完成，必须在 M8 兼容性测试中补齐**。
   已知风险：Safari 对 OGG Vorbis/Opus 的支持历来与 Chromium 不同，格式选择需在补齐后复核。
2. **只测了 WAV/PCM 解码**，压缩格式（MP3/Opus/AAC）的解码成本**未测**。
3. `outputLatency` 报 0，该值在本环境下不可信，未做进一步验证。
4. **未测实际播放延迟与音画同步精度** —— 这需要真实音频资源与游戏逻辑，属 M2 范围。
5. **未测移动端**（本阶段已决定目标平台为仅 PC 浏览器，符合范围）。
6. 测试环境为自动化派发的 CDP 输入事件（trusted event）。真实玩家输入存在微小差异，
   但用户激活语义一致，结论适用。
