第 0 章  本文档的效力与阅读前提
--------------------------------------------------------------------------------
0.1 效力
    本文档确认 M0 阶段的技术选型，是 M1 及之后所有实施的**前置约束**。
    除非走变更流程（见第 7 章），本文档中的选型项不得擅自更改。

0.2 阅读前提（重要）
    本文档中每一项结论都标注了【依据类型】，只有两类：
      【实测】 —— 有可复现的实测数据支撑
      【指定】 —— 由项目负责人直接决定，不依赖实测
      【未测】 —— 尚未验证，明确标注为缺口
    禁止把【指定】当作【实测】引用，禁止把【未测】当作已知条件使用。


第 1 章  核心选型决定
--------------------------------------------------------------------------------
1.1 渲染引擎
    决定：**Three.js 0.186.1**
    依据类型：【指定】
    决定方式：项目负责人直接指定。
    实测数据角色：辅助支持，**不构成完整证明**。

    必须如实记录的证据强度问题：
      (1) 引擎对比测试只完成了一部分。Babylon.js 端在加入 sync 开关后出现页面
          加载失败（未定位），因引擎已定，未继续追查。因此对比数据不完整。
      (2) 本机显示器为 165Hz，vsync=on 时两端 FPS 均精确停在 165.01，
          该数字**不能**用于比较引擎性能，只能说明两者都未跑满。
      (3) 唯一一次有效的解锁对比（vsync=off）中，frameP95 ≈ cpuP95，
          说明测的是 CPU 提交吞吐而非 GPU 能力，不能表述为"可达到的帧率"。

    有效信号（方向一致，强度中等，仅供参考）：
      - Three 的 CPU 单帧 P95 约为 Babylon 的 1/5（0.8ms vs 4.1ms）
      - Three 的堆内存峰值约为 Babylon 的 1/2（28.14MB vs 53.87MB）

    诚实结论：选 Three.js 是**负责人的决策**，实测数据与之一致，
    但没有把 Babylon 跑完整。这一差别必须保留在文档中，避免日后误认为
    "当初是数据选出来的"。

1.2 候选排除记录
    PlayCanvas：纸面排除。依赖其在线编辑器与账号体系，与"可自研、可控包体"的
                项目前提冲突，未做实测。
    Babylon.js：实测后放弃。数据不完整（见 1.1）。

1.3 构建工具
    决定：**vite 8.3.4**（rolldown 内核，oxc 压缩）
    依据类型：【指定】
    实测补充：构建验证通过。注意 vite 8 已改用 oxc 压缩，
              配置中指定 minify:'esbuild' 会直接构建失败。

1.4 目标平台
    决定：**仅 PC 浏览器，本期不做移动端**
    依据类型：【指定】
    连带影响：
      - 《流程文档》第 1.2 节目标用户、第 2.6 节、第 9.5 节输入方案需同步改写
      - M0-4「触屏 FPS 操作方案验证」从 M0 移除
      - 第 9 章性能指标只需覆盖桌面浏览器
      - 移动端相关风险（R04）降级，转为后续版本议题


第 2 章  选型对比实测数据（存档）
--------------------------------------------------------------------------------
说明：本节数据因 1.1 所述原因**不完整**，仅作存档，不作为选型依据。

2.1 等价场景定义
    两端读取同一份 scenes/spec.json：48~120 单位地面、200 静态障碍、
    150 动态物体、400 粒子、方向光+环境光、开启阴影（1024）、pixelRatio=1。
    两端一律使用独立 Mesh，禁止实例化，保证优化程度对等。

2.2 实测结果（目标机：i5-13600KF / RTX 3060 / Windows 11 / Chrome 153）

    条件                     Three.js            Babylon.js
    ------------------------------------------------------------------
    vsync=on  avgFps         165.01              165.01      ← 被 165Hz 锁住，无效
    vsync=on  frameP95       6.2 ms              6.2 ms      ← 无效
    vsync=on  heapPeak       14.89 MB            47.26 MB
    vsync=off avgFps         1253.25             500.47      ← 实为 CPU 提交吞吐
    vsync=off frameP50       0.7 ms              1.4 ms
    vsync=off frameP95       0.9 ms              4.4 ms
    vsync=off cpuP95         0.8 ms              4.1 ms
    vsync=off heapPeak       28.14 MB            53.87 MB

    两端实际 WebGL 渲染器字符串均为：
      ANGLE (NVIDIA, NVIDIA GeForce RTX 3060, Direct3D11 vs_5_0 ps_5_0, D3D11)
    （本机存在 MuMu 虚拟显示适配器，已用 --force_high_performance_gpu 排除）

2.3 已知不可比项（两端无法做到完全等价）
    - 阴影算法：Three PCFSoft vs Babylon PCF
    - 材质模型：Three MeshStandardMaterial vs Babylon PBRMaterial（后者实现更重）
    - 粒子点尺寸单位：Three 为世界单位，Babylon 为像素


第 3 章  由实测导出的技术约束（M1 必须遵守）
--------------------------------------------------------------------------------
以下每一项都有实测依据，属**硬约束**。

3.1 AI 寻路【实测】
    实测单次成本：A* 0.0184 ms、流场全图重算 0.0718 ms、视线射线 0.000093 ms。
    实测每帧占比：N=400 时 AI 仅占帧 CPU 的 8.9%，渲染占 91%。
    实测最坏帧：N=400、6x CPU 节流下，A* 方案单帧寻路 68.29 ms，
                流场方案 2.38 ms，差 20~30 倍。

    约束：
      C-1 禁止 N 个 AI 在同一帧无限制发起 A* 查询。必须实现每帧查询预算
          （排队处理），单帧寻路耗时上限 2 ms。
      C-2 常态移动使用共享流场；个体独立 A* 仅用于少数精英 AI。
      C-3 视线检测每帧全量执行，不做错峰降频（成本可忽略，简化逻辑并提升响应）。
      C-4 同屏 AI 数量上限**暂不写死**。真实上限由渲染决定，
          须在 M7（正式美术资源）与 M8（优化）后重新测定。

3.2 渲染与几何【实测】
    实测：约 312 个独立墙体 Mesh 在 6x CPU 节流下约占 15.9 ms/帧，
          远超 AI 成本。渲染占帧 CPU 的 91~98%。

    约束：
      C-5 关卡静态几何**必须**实例化或合批，禁止逐个 Mesh 提交。
      C-6 在 6x 节流（模拟低端 CPU）下，单帧 draw call 预算约 200~250 个。
          该数字为派生值：15.9ms ÷ 312 Mesh ≈ 0.051 ms/Mesh，
          60fps 预算 16.67ms 扣除其他系统约 5ms 后得约 240 个。
          该派生值须在 M8 用真实关卡复测后修订。

3.3 音频【实测】
    实测：无用户手势时 `AudioContext.resume()` **永不 settle**（既不 resolve
          也不 reject）。解锁成本 15.7~25.4 ms。AudioContext 创建 25.7~43.2 ms
          （同步阻塞）。

    约束：
      C-7 **禁止**在任何模块顶层或加载流程中 `await audioContext.resume()`。
          该写法会导致加载流程永久挂起，且无异常、无日志、无超时。
      C-8 必须实现"音频解锁门"：在首个可交互界面上的一次用户手势内，
          一次性完成 创建 AudioContext → await resume() → 播放静音占位。
      C-9 未解锁前，所有音频播放请求走"静默丢弃 + 排队"分支，
          不得抛异常中断游戏逻辑。
      C-10 AudioContext 创建**不得**放入进图加载的关键路径。

3.4 打包与传输【实测】
    实测首包（最小可运行游戏骨架 + three）：
      brotli 106.7 KB / gzip 130.0 KB / raw 524.4 KB
    实测 tree-shaking 收益上限：仅 40.1 KB brotli（全量 146.8 → 最小集 106.7）。
    实测命名空间导入与命名导入体积**完全相同**（差 0 KB）。

    约束：
      C-11 CDN **必须**开启 brotli 传输。相对 raw 省 80%，
           不开则首包体积凭空翻数倍。
      C-12 不得把"必须用命名导入"写进代码规范 —— 本打包器下无体积收益。
           应改为禁止"动态属性访问引擎成员"（如 THREE[变量名]），
           该写法会破坏 tree-shaking（此项**未测**，见第 5 章）。
      C-13 M1 必须建立体积门禁：每次构建输出首包 brotli 大小并记录趋势。
      C-14 分包边界按资源划分：首发地图资源进首包；其余地图、音频、
           局外界面资源按需加载。**引擎无法分包**（首屏即需渲染）。

3.5 计时与测量纪律【实测】
    实测：Chrome 默认把 performance.now() 精度限制到 100µs，
          导致 AI 成本全部量成 0。
    修复：静态服务加 Cross-Origin-Opener-Policy: same-origin 与
          Cross-Origin-Embedder-Policy: require-corp，
          分辨率恢复到 0.005 ms。

    约束：
      C-15 所有子毫秒级性能测量必须在跨源隔离环境下进行，
           并回读计时器分辨率自检值；若为 0.1ms 则数据不可信。
      C-16 低于计时器分辨率的操作必须用批量微基准（执行 N 次再相除），
           禁止用逐次计时。
      C-17 性能判定以帧时间与 CPU 耗时为判据，**不得以 FPS 为判据**
           （FPS 会被刷新率、锁帧、异步流水掩盖）。

3.6 输入与浏览器保留快捷键【实测，M1 期间新增】
    实测事实：浏览器保留快捷键由浏览器 UI 层处理，**不经过页面的可取消路径**，
              因此 `preventDefault()` 对它们**无效**。页面唯一能做的防御是
              **不把这些组合用作游戏动作键**。

    真实事故：M1 曾把"蹲下"绑定到 Ctrl。玩家蹲下前进 = Ctrl+W，
              在 Chromium 系浏览器（含 QQ 浏览器）上**直接关闭标签页**，
              且游戏无法拦截。已改为 C 键。

    约束：
      C-18 **游戏动作键严禁绑定 Ctrl / Alt / Meta**。
           理由：玩家必然会把它与 WASD 同时按下，从而触发浏览器保留快捷键。
           已知会撞上的组合（非完整列表）：
             Ctrl+W 关闭标签页   Ctrl+Shift+W 关闭窗口   Ctrl+T 新标签页
             Ctrl+N 新窗口       Ctrl+Tab 切换标签页     Ctrl+1..9 切换标签页
             Ctrl+R / F5 刷新    Ctrl+D 收藏             Ctrl+S 保存
             Ctrl+P 打印         Ctrl+O 打开文件         Ctrl+F 查找
             Ctrl+L 定位地址栏   Alt（Windows 上可能激活菜单栏）
      C-19 按键自定义功能（M2/M5 的设置界面）**必须拒绝** Ctrl/Alt/Meta 组合，
           并在 UI 上说明原因，不能让玩家自己绑出一个会关页面的键。
      C-20 指针锁定属于"可失败的外部权限"，其请求失败（Promise 拒绝或同步抛错）
           **必须静默降级，绝不能中断游戏逻辑**，也不得产生未捕获的 Promise 拒绝。
           失败兜底：玩家点击画面时再次请求。
      C-21 **同一按键不得绑定到多个动作**。一次按键触发多个动作属于功能性错误，
           且往往表现为"某个功能莫名奇妙地不好用"，很难定位。
           真实事故：M1 加入左右探头后，`leanRight` 与 `interact` 都绑了 KeyE ——
           右探头与搜刮被同一次按键同时触发。已把搜刮改为 F。
           按键自定义 UI（M2/M5）必须在保存绑定前执行本项校验。

    回归防护（已落地）：
      tools/audit-keybindings.mjs —— 静态审计，直接 import 代码里的绑定表
      （不是正则抓文本，改代码审计必然随之变化），两条硬性规则：
        规则 1  游戏动作不得绑定 Ctrl/Alt/Meta
        规则 2  同一按键不得绑定到多个动作
      违规即 exit 1。两条规则均已做注入自检：
        把 crouch 改回 Ctrl  → 规则 1 报错
        把 interact 改回 KeyE → 规则 2 报错（精确指出 KeyE 被 interact/leanRight 占用）
        还原后文件哈希逐字节一致。

      必要性与教训：
        - CDP 合成的按键走渲染进程，**不会触发浏览器 UI 快捷键**，
          因此规则 1 那类缺陷**自动化冒烟测试天然抓不到**，只能靠静态审计 + 人工试玩。
        - **规则 2 的存在本身就是一次教训**：审计初版只查规则 1，
          于是 KeyE 冲突发生时审计全绿 —— 一个只检查某类问题的守卫，
          会让人误以为其他类问题也有人管。新增加键位时必须同时补检查项。

第 7 章  选型变更流程
--------------------------------------------------------------------------------
7.1 触发条件
    只有出现以下任一情况才允许提出变更：
      - 实测证明当前选型无法达到《流程文档》第 9 章性能指标，且已穷尽优化手段
      - 出现阻断级缺陷且无法在 2 周内修复
    禁止以"另一个看起来更好""团队更熟悉"为由提出变更。

7.2 流程
    提出 -> 影响评估（工作量/返工范围/排期影响）-> 制作人与主程签字 -> 更新本文档版本
    未走完流程的变更一律回滚。

7.3 已冻结项
    以下项自本文档生效起冻结，变更需走 7.2：
      - 渲染引擎（Three.js 0.186.1）
      - 构建工具（vite）
      - 目标平台（仅 PC 浏览器）
      - 第 3 章全部硬约束 C-1 ~ C-17
