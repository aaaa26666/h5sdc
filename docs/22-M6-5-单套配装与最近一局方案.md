## 三、设计

### 3.1 数据模型：从 `loadouts[]` 收敛成一份 `loadout`

```
profile.loadout   = { primary, secondary, body, head, backpack, rig, carry: {backpack[], rig[], safe[]} }
profile.lastRaid  = { mapId, atMs, slots{…}, carry{ backpack[], rig[], safe[] } }   // 只记"带的是什么"
```

- 删掉 `loadouts[]` / `activeLoadoutId` / `maxPresets` 与 `addPreset` / `removePreset` /
  `setActivePreset` / `renamePreset`；`updatePreset` 改名/简化为 `updateLoadout(profile, patch, cfg)`。
- `lastRaid.carry` 存**`itemId + count + 落点`**，不存 `uid`：uid 是"这一件在哪"的编号，
  下一局仓库里的东西已经换了（上一局的被带走/丢掉，新捡的进来），按 uid 恢复必然对不上。
- 存量档案迁移：**清空配装**（裁定 7）。装备与弹药都还在仓库里，玩家重配一次即可；
  迁移必须在 `sanitizeLoadoutShape` 里做并留 `repairs` 痕迹（不走 `MIGRATIONS`，理由同 M6-4：
  迁移函数会静默丢东西，而这里必须让"配装被清空过"这件事**可观测**）。

### 3.2 「最近一局」的恢复算法

```
restoreLastRaid(profile, cfg):
  对 lastRaid.slots 的每个槽：仓库里有同 id 的装备 → 装上（走 equipFromStash 的同一条路径，按 uid）
  对 lastRaid.carry 的每一格：
      仓库里找 itemId 相同、且 count 恰好等于目标数量的条目 → 优先整条搬进该格
      否则找任意一条同 itemId → 拆出目标数量（复用「拆分」的 core 函数）再搬进该格
      两者都没有 → 记入 missing
  返回 { profile, missing }
```

**为什么优先"数量恰好"的整条**：仓库里 60 发一盒与 30 发半盒是两条不同条目，
优先整条可以避免"为了凑 30 发把一盒 60 发拆开"这种无谓的碎片化。

### 3.3 缺件补齐（花钱）

**已裁定（2026-10-14）**：

| 问题 | 裁定 |
|---|---|
| 价格取哪个？ | 走 `core/shop.js` 的 `buyPriceOf`（价格只有一处实现，含买卖价差与等级解锁规则） |
| 某件**按等级未解锁**（商店买不到） | **不补那一件**，但在弹窗里**单列**"不可购买（未解锁）"，其余照补；不整单拒绝、也不新增溢价绕过解锁的规则 |
| 粒度 | 只补 `lastRaid` 清单里缺的那些，**不超过**上一次的数量 |

- 弹窗文案必须**明示花费与清单**（"缺 X 件，将花 Y 货币"），确认才执行；货币不足则拒绝并告知差多少。
- 补齐后**自动放回对应的格**（复用 3.2 的同一套落点逻辑，不另写一份）。

### 3.4 「最近一局」恢复的数量口径（已裁定）

| 问题 | 裁定 |
|---|---|
| 仓库里只有**数量不同**的同种物品（要 30 发、仓库只有 60 发一盒） | **拆出目标数量**（严格还原上一次的布局与负重），复用既有的「拆分」能力，不新增机制 |
| 优先顺序 | 先找 `count` **恰好相等**的整条搬进去；没有才从任意一条同种物品**拆出**目标数量 |

**为什么优先"数量恰好"的整条**：仓库里 60 发一盒与 30 发半盒是两条不同条目，
优先整条可以避免"为了凑 30 发把一盒 60 发拆开"这种无谓的碎片化。

### 3.5 迁移提示（已裁定）

旧存档迁移清空配装后，**在大厅提示一次**"配装已按新版本重置"（装备与弹药仍在仓库里，一件不丢）。
提示只出现一次，之后不再挂（沿用 `lobby.toast` / 既有横幅口径，不新开提示形态）。

### 3.6 UI

- 「装备」页原预设条（切换/新增/删除）位置让给两个按钮：**「最近一局」** 与
  （在有 `lastRaid` 时才可点）**「一键补齐」**（补齐在弹窗里确认）。
- 恢复后若有缺件，用既有的 `lobby.toast` + 面板上的缺件清单呈现（沿用 `reasonText` 的文案口径），
  不新开一种提示形态。

## 五、风险

| 风险 | 说明 | 对策 |
|---|---|---|
| **迁移不可逆** | 清空配装是裁定，但玩家会觉得"我的配装没了" | 装备与弹药**都在仓库里**，一件不丢；迁移留 `repairs` 痕迹并在大厅提示一次"配装已按新版本重置" |
| **`presetId` 参数面很宽** | `carryPlaceFromStash` / `carryTakeToStash` / `carryMove` / `equipFromStash` / `unequipToStash` / `updatePreset` 都带 `presetId` | 收敛后这些函数的签名一起去掉该参数；**不留"传什么都行"的兼容分支**（那会让旧调用静默走错） |
| **补齐花的是玩家的钱** | 自动购买是最"危险"的一类交互 | 必须弹窗明示清单与总价、必须二次确认、绝不自动执行 |
| **`lastRaid` 与"进局检查"的边界** | 恢复可能瞬间把网格塞满/超容量 | 恢复后立刻跑一次 `auditCarryBeforeRaid`，有问题就走既有的警告页（不另写一套判定） |

## 六、本方案明确不做

- 难度选择（已裁定推迟）。
- 局内背包网格 UI（M6-4 已裁定"局外新增保险箱网格，局内沿用"）。
- 多套配装的"另存为/导入"等替代品：裁定是**不做预设**，不是换个名字继续做。

### 7.3 测试（每条都要能失败）

- 单测：旧档迁移后**配装为空且 `repairs` 有痕迹**；`restoreLastRaid` **优先数量恰好**的整条；
  数量不等时**拆出目标数量**且总量守恒；缺件进 `missing`；`refillLastRaid` 只补到上次的数量、
  **未解锁的单列**且不扣钱、货币不足**整单拒绝**；恢复后 `auditCarryBeforeRaid` 不再拦下。
- 端到端：两个按钮存在且可用；点「最近一局」后网格内容与上次一致；
  点「一键补齐」后**货币真的减少**、且随后能直接进战区；未解锁件的提示出现在弹窗里。
- 反向断言：`tools/smoke.mjs` 的静态源码扫描要把 `addPreset|removePreset|setActivePreset|renamePreset`
  一并列为**禁用**（与 `ammoInc` 那批同级），证明"多套预设"不是被藏起来而是被删掉了。
