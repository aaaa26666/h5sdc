### 5.1 M5-BUG-01：大厅「查看结算」栏在无待结算战局时恒显（`hidden` 被 author display 规则取消）

| 项 | 内容 |
|---|---|
| 编号 | **M5-BUG-01** |
| 分级 | **S2** —— 不丢档、不阻断玩法；但 M4-7 交付的"上局未正常结束"提示**实际不可用**：没有待结算战局时它照常画在屏幕上，会误导玩家"有战局要结算"（点了却无事发生）。未定 S1 的理由：不涉及数据丢失 |
| 发现于 | M5-1 大厅验收（制作人肉眼发现：「如果没有待结算的战局就不要在大厅显示查看结算一栏」） |
| 位置 | `index.html:203`（`hidden` 属性）/ `index.html:99`（`.row{display:flex}`）；`src/main.js` 的 4 处手写写点；`src/ui/lobby.js:49-51`；`tools/smoke.mjs` 的 4 处断言 |

#### 现象（实测）

| 步骤 | 观测 |
|---|---|
| 打开页面、**没有任何待结算战局** | 大厅里「上局未正常结束（刷新 / 关闭页面）… 点击查看结算 ›」**照常显示**，连虚线下边框都在 |
| 用布局盒口径量它 | `getClientRects().length = 1`、`height = 31.796875px`（**占了 31.8 像素**） |
| 同一时刻它的 attribute | `hidden = true` —— 也就是"代码认为自己已经把它藏好了" |

#### 根因

UA 样式表用 `[hidden] { display: none }` 实现 `hidden`，**但 WHATWG HTML 明示它可以被 author 的 display 规则取消**：

> "Because this attribute is typically implemented using CSS, it's also possible to override it using CSS.
> For instance, a rule that applies `'display: block'` to all elements will **cancel** the effects of the `hidden` state."

`#interruptedNotice` 同时带 `class="row"`，而 `.row { display: flex }` 与之**同 specificity**、author 必然胜出
→ UA 的 `display:none` 被取消，元素照常渲染。`main.js` 里 `if (loadCheckpoint()) …` 的逻辑本身没错 ——
**它写的是 attribute，浏览器却看不见 attribute。**

#### 为什么没被抓到

那批断言全部读 `document.getElementById('interruptedNotice').hidden`，那是 **IDL 属性反射**，
只反映 attribute 有无，**与"是否真的渲染"无关** → 无论页面长什么样都恒绿。

★ **必须如实写明：M4-7 当初关于该提示"可见 / 已收起"的实测证据是空的。**
它只留下 attribute 读数，没有任何渲染口径（或截图）证据。也就是说 M4-7 报告里
"提示可见 ✓"这类结论，在本次修复前**从未被真正验证过**。这不是"测了但漏了边界"，
而是"这条断言从写下那天起就不可能失败"。

旁证：同一文件里早已为**结算页**补过同类断言（注释原文：「只查 `raidResult` 不够……
这条断言就是为了让'结算页真的画出来了'成为事实」）—— 说明这个教训此前**只补了一处、没补全**。

#### 修复

1. `index.html` 新增全局 author 规则 `[hidden] { display: none !important; }`（附规范依据注释）。
   用 `!important` **不是为了打赢某条具体样式**，而是让 `hidden` 的规范语义不受任何 author
   display 规则与书写顺序影响地恢复。已逐项核对：全项目**仅此一个元素**用 `hidden` 属性，
   爆炸半径 = 1；`.screen.on` / `.btn` / `.seg.on` / `.on` 系列全部是 class 机制，与之正交。
2. **可见性收口**：原由 4 处各写一遍"该不该显示"（`settleInterruptedRaid` / `startRaid` / 初始化段 /
   点击守卫分支），现全部删除，改为 `showLobby()` **一处**从 `loadCheckpoint()` 推导 ——
   符合"唯一真值"：有快照就显示、没有就不显示，结构上不可能再漏关。
   ★ 不变式因此从"清快照必须在收起提示之前"变成更强的「**showLobby() 必须在结算之后被调用**」。
3. 断言口径改造：新增 `isVisible(selector)`（`getClientRects().length > 0`；元素缺失时**抛错**而不是静默返回 false），
   4 处断言全部改用它。**不用 `offsetParent`**：`#screenLobby` 是 `position:fixed` 的 `.screen`，
   固定定位元素的 `offsetParent` 恒为 null，会把"可见"误判成"不可见"。
4. 新增"不占位"断言（`rects === 0 && height === 0`）—— 本缺陷的实际观感是**占据了一行高度**，
   只断言"不可见"不够。

#### 证据链

| 环节 | 证据 |
|---|---|
| 缺陷真实存在 | 修复前，3 条断言 FAIL：`幂等`（提示真实可见=true）、`大厅无待结算战局时…不出现且不占位`（**rects=1 height=31.796875**）、`★ 补结算后回到大厅，提示不再出现`（大厅可见=true 提示真实可见=true） |

| 全量回归 | 端到端 **177/177**、单测 **346/346**、`verify-prod-bundle` 全 PASS、首包 brotli 156.7/200 KB（**体积零变化**） |

### 5.2 M5-BUG-02：第 ⑩ 组的「落地缓冲」断言是**竞态**，会随机假红

| 项 | 内容 |
|---|---|
| 编号 | **M5-BUG-02**（**测试缺陷**，不是产品缺陷） |
| 分级 | **S3** —— 不影响产品行为；但会随机产生假红，侵蚀"测试可信"这个前提 |
| 发现于 | M5-BUG-01 修复后的复跑（连续 2 次 `下沉峰值 0.0000m`），用临时探针定位 |
| 位置 | `tools/smoke.mjs` 第 ⑩ 组「落地产生相机下沉（落地缓冲）」「落地后下沉会回弹」两条断言 |

#### 现象与实测

| 步骤 | 观测 |
|---|---|
| 修复后第 1 次复跑 | 第 ⑩ 组两条断言 FAIL，`下沉峰值 0.0000m` |
| 第 2 次复跑 | 同样 FAIL，同样 `0.0000` |
| 第 3 次复跑 | 全部 PASS，`下沉峰值 0.0379m` |
| **探针（同一位置、同一份代码，连跳 10 次）** | **命中率 8/10**。失败与成功的两次，`onGround=false vy≈3.26` 与 `采样 9 次` 完全相同 |

#### 根因

`landingDip` 是个**瞬态**：落地时置为冲击量（实测约 0.04~0.057），随后逐帧
`dip = max(0, dip - recoverSpeed * dt)` 衰减（`src/core/movement.js` 的 `updateLanding`），
**只活几十毫秒**。而断言的采样循环是「`snap()` + `sleep(50)`」，实际周期约 60~90ms
（`page.evaluate` 往返 + 50ms），于是**能否采到那一帧全凭相位**。
（附带排除一个直觉猜测：`landings++` 只在 `impactSpeed > 0` 时发生，见 `applyLandingImpact`
的前置分支，所以**不存在"空落地"** —— 纯粹是采样窗口太稀。）

#### 为什么现在才暴露

**不是本次改动引起的产品回归**：这两条断言测的 `src/core/movement.js` / `src/gameplay/player.js`
在 M5-BUG-01 中**一行未改**。但 M5-BUG-01 顺带改了 `tools/smoke.mjs`（新增 4 处 CDP 调用与 600ms sleep），
**改变了后续采样的相位**，把原本约 20% 的偶发失败变成了一次连续两次 ——
也就是说：这条本来就不可靠的断言，被另一个正当改动"照出来了"。

#### 未修复（本次刻意不动）

不在 M5-BUG-01 的范围内，按项目纪律**只登记、不顺手改**。建议的最小修法（供后续评估）：

- 去掉或大幅降低采样循环里的 `sleep(50)`（降到 ~5ms），用密集采样把那几十毫秒的窗口罩住 ——
  这是**收紧**而不是放宽；或
- 在页面侧累计"本次跳跃的最大下沉"再一次性读回（需要新增一个 DEV 探针字段，属 `src/` 改动）。

### 5.3 已排除的疑点（记录下来，避免下次重复怀疑）

| 疑点 | 排查结论 |
|---|---|
| 局内世界重建后，小地图会不会画的是上一局的地形 | 不会。`minimap.js` 的地形缓存按**层号**缓存，且内容只由 `level.nav.blocked` 决定；同一张地图重建后阻塞图逐格相同，因此缓存命中是**正确**的复用。若将来支持多张不同尺寸的地图，必须把 `W/H/cell` 纳入缓存键 |
| 重建后 `weaponSys` 的随机流会不会与上一局不同（导致后坐力手感变化） | 不会。`weaponRng` 每局用同一个种子（`cfg.level.seed + 7717`）重建，序列**逐局相同** —— 这是可复现性，测试依赖它 |
| 跨局残留的模块级变量还有没有漏的 | 已逐个清点：`combatStats`（就地清零）、`kills`、`lastExtract`、`footstepsAccum`、`isPaused`、`pauseStartedAt`、`pausedTotalMs`、`lockGraceUntilMs` 都在 `resetRaidState()` 里复位；`raidId` / `checkpointLastWrite` 在 `startRaid()` 里重取；`lastRaidResult` **有意保留**（它是"上一局的结算"，供结算页与断言读取） |
| 主音量写 0.35，`audio.gain` 读回来是 0.3499999940395355，是不是倍率接错了 | **不是缺陷，是断言口径错**。`master.gain.value` 是 Web Audio 的 `AudioParam`，其值按 **float32** 存储：0.35 的最近 float32 表示就是 0.3499999940395355（0.525 → 0.5249999761581421 同理，均与 float32 舍入逐位一致）。断言容差必须 **≥ float32 在该量级的量化步长（约 3e-8）**，原写的 `1e-9` 比它还小一个数量级，等于在测"浮点存储格式"。已改为 `1e-6`，并**新增"高低两档的比值 = 配置表倍率之比"**这条与基线无关的断言（倍率接错必然露） |
| 从大厅再进战区，`remainingMs` 是 779516 而不是 `raid.timeLimitMs`（780000） | **不是缺陷，是断言口径错**。RAID 态的 `remainingMs = 时限 − 已过时间`，而快照本身要花掉数百毫秒，所以它**不可能**等于整局时限；原断言等于假设"快照零耗时"。已改为断言"比上一局结束时**更大**（只有重置才会变多）+ 距满格 < 10s"，并让第一局先烧掉 ≥1.2s，使"计时归零"可被观测（实测上一局烧 2833ms、新局仅 484ms） |

## 九、缺陷登记（M5-2 ~ M5-8 新发现）

> 格式沿用前文：编号 + 分级 + 发现于 + 位置 + 现象 + 根因 + 为什么没被抓到 + 修复 + 证据链。
> 定位方式：`grep -rn "M5-BUG-0" src/ tools/`

### 9.1 M5-BUG-03：局内直接"返回大厅"会**静默丢装备**（S2）

| 项 | 内容 |
|---|---|
| 编号 | **M5-BUG-03** |
| 分级 | **S2** —— 不崩、不阻断；但玩家的一整套行装凭空消失，且**没有任何结算记录** |
| 发现于 | M5 冒烟新增组（"换一把枪后局内随之改变"失败，`weapon=pistol_p9`） |
| 位置 | `src/main.js` 的 `returnToLobby()` |

**现象**：在局内（`flow === RAID`）调用"返回大厅"时，进局时从仓库扣走的配装**既不还回、也没有结算** —— 仓库少了一套装备，档案里没有这一局的任何记录。

**根因**：M5-3 引入"进局扣件 / 结算还件"之后，"回大厅"多了一个前提：**必须先结算**。而原 `returnToLobby` 只在 `flow === ENDED` 时做状态迁移，`RAID` 状态下它直接 `leaveRaidWorld()` —— 扣掉的配装永远回不来。

**为什么没被抓到**：它需要"局内直接回大厅"这条非常规路径；玩家的常规路径（结算页 → 返回大厅）覆盖不到。是新增的冒烟组把这条路径走出来了。

**修复**：`RAID` 状态下先按「放弃本局」结算，再迁移状态 —— 于是**任何**回大厅的路径都不会丢装备。

### 9.2 M5-BUG-04：取件清单被跨局复位清掉（S2，与 9.1 同源）

| 项 | 内容 |
|---|---|
| 编号 | **M5-BUG-04** |
| 分级 | **S2** —— 与 9.1 叠加造成同一后果的另一半 |
| 发现于 | 冒烟断言"进局扣件清单里有主武器与弹药"报 `0 项` |
| 位置 | `src/main.js` 的 `resetRaidState()`（我一度在其中写了 `raidTaken = null`） |

**根因**：`resetRaidState()` 是 `enterRaidWorld()` 的第一步，而 `startRaid()` 的顺序是"先 takeLoadout（写 raidTaken）→ 再 enterRaidWorld（resetRaidState）" —— 刚写好的清单立刻被清空。于是撤离时"没用完的配装"还不回、阵亡时也不计入损失统计。

**修复**：把 `raidTaken` 从 `resetRaidState()` 移出 —— 它属于"本局的输入"，不是"跨局的残留状态"。修复处写明了为什么不能在那里清。

### 9.3 M5-BUG-05：空档案路径的 `repairs` 不可观测（S3）

| 项 | 内容 |
|---|---|
| 编号 | **M5-BUG-05** |
| 分级 | **S3** —— 不影响玩法；但"存档曾经是空的 / 曾经坏过"在界面与 DEV 接口里都读不到 |
| 发现于 | 冒烟"存档被清空：第一次加载记账为 empty"失败 |
| 位置 | `src/core/profile.js` 的 `parseProfile()` 空档案分支 |

**根因**：该分支直接返回 `{ profile: createNewProfile(...), repairs: ['empty'] }`，**没有把 `_repairs` 挂到档案对象上** —— 而 `__m2.profile()` 与界面读的是档案上的 `_repairs`。调用方一取 `.profile`，修复记录就丢了。

**修复**：空档案路径也写 `profile._repairs`。修复必须**可观测**，否则"存档坏了但看起来正常"永远不会被发现。

**附带：一处断言口径错（不是缺陷）** —— 我最初写的是"清空后重进仍要有 repairs"。那是错的：第一次加载已把新档写回，第二次加载读到的是一份**合法**档案，自然没有可修的东西。断言已改为"重进后仍是全新档案、不留半坏状态"，而"记账为 empty"移到**第一次**加载上。
