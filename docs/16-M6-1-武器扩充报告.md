## 三、数值平衡：数字是**解出来的**，不是写的

**方法**：每类定 6 个角色 → 由角色**反解**数值 ——
躯干伤害由"无甲致死发数 N"反算（`(N-1)d < 100 ≤ N·d`）、爆头伤害由类别爆头上限反算、
扩散恢复由本枪的恢复档次反解速率。全部用 `src/core/ballistics.js` 的
`computeTtk` / `spreadRecoverySeconds` 验证 —— **与 `tools/ttk.mjs` 同一份实现**。
生成器保留为 `tools/gen-weapons-m6-1.mjs`（设计期工具，不在验证链上）。

**为什么不能直接给数**：第一版直接给伤害与射速，**13/30 未达标**。卡住的是四条硬判据，
不是体积：

| 判据 | 卡住的东西 |
|---|---|
| 爆头发数上限 | pistol≤2 / dmr≤1 / rifle≤2 / smg≤3 |
| 躯干 TTK 带 | 每类一条，很窄（步枪仅 0.26~0.5s） |
| 扩散恢复上限 | pistol/smg 0.8s、rifle 0.9s、dmr 1.6s、shotgun 1.2s |
| 三级甲全局 ≤1.2s | 慢射高伤武器最容易被它拦住 |

**恢复速率刻意拉开档次**（不是"都解到刚好达标"）：同类别 6 把的恢复极差
pistol 0.288s / smg 0.238s / rifle 0.235s / shotgun 0.363s / dmr 0.540s。
方案 v2 §三 曾把"扁平化"标为待办，本次已消除。

## 四、掉落池：实测推翻了初稿

方案初稿让 **2 把**进池（`rifle_ak762`/epic + `dmr_g28`/legendary）。
实测（校验器固定种子 20260301，结果可复现）：

```
基线（不入池）        贪（全图）中位 23580   ✔ 落在 22000~36000
2 把长枪入池          贪（全图）中位 21100   ✘ 跌破下限（−10.5%）
```

**扫描后确认拖累主因是体积，不是价值**（同一把枪的稀有度位置几乎不影响结论）：

| 入池组合 | 中位 | 判定 |
|---|---|---|
| 基线（不入池） | 23580 | ✔ |
| 仅 `pistol_mk23`（rare，2×2） | 23280 | ✔ 只降 300 |
| **仅 `rifle_ak762`（epic，2×4）← 最终采用** | **22810** | ✔ 降 770 |
| 仅 `dmr_g28`（legendary，2×4） | 22040 | ✔ 贴地板 |
| mk23 + ak762 | 22400 | ✔ 余量仅 1.8% |
| mk23 + g28 | 21680 | ✘ |
| ak762 + g28（初稿） | 21100 | ✘ |

机制：2×4 的枪占 8 格，掉一把就挤掉好几件小件 ——「被迫留下」从 28% 升到 32%。
**收敛为只加 1 把 epic**（余量 3.7%）。若日后要再加，**优先 2×2 的小体积**，不要加第二把长枪。

### 新增的门禁与断言

1. **`ttk.mjs --gate`（新增）**：本工具在此之前**只打印、从不 exit 非零** ——
   "数值平衡完成"没有任何自动守卫。现加 `--gate`：**只有 OUT 阻断，临界仅警告**
   （4 把一枪致死的霰弹枪天然贴着区间下沿，若临界也阻断会每次构建都被挡下）。
2. **单测 6 条**：武器数 ≥6、每类 ≥2 把、每把都有设计目标、全部落在设计目标内、
   每把都可在商店买到、**原有 5 把基准数值未被顺带改动**。
3. **端到端 16 条（`--only=武器` 可单独跑）**：覆盖 3 种口径与 2 个槽位，
   逐把断言"能授予 → 进局手上就是它 → 带足弹药 → 开火有效（弹匣真的减少）"。
   ★ 这一层是**纯逻辑断言看不见的**：表里合法 ≠ 玩家拿得到 ≠ 拿到能开火，
   而批量扩充恰恰最容易制造"写进表里但没人能拿到"的缺陷。
4. **新 DEV 夹具 `grantWeapon(ref, rounds)`**：按 id 授予任意武器 + 对应口径弹药。
   旧的 `grantTestKit` 固定给 5 把老枪，扩到 30 把后覆盖率会漏。
   已同步加入 `verify-prod-bundle.mjs` 的 `FORBIDDEN` 清单。

## 六、过程中的三次自我纠错（都留在代码注释里）

1. **价值公式用射速间隔当因子** → 算出 RSH 手枪价值 **10582**（比 SR-25 的 3200 还贵）。
   射速间隔是"节奏"，不是"价值"。改为**按类别分档、以既有 5 把为锚**的价梯。
2. **物品形状按弹匣大小算** → 产出 2×3 的步枪，与既有"手枪 2×2 / 冲锋枪 2×3 / 长枪 2×4"的约定不符。已对齐。
3. **掉落池一次加 2 把长枪** → 中位收益跌破下限（见 §四）。

另有一次**操作失误**：用 `git checkout` 回滚注入自检时，把本次尚未提交的 30 把一起回滚了。
生成器是确定性的，已完整重产出并逐项复核（30 把 / 22 件 / 40 条在售 / 字段一致）。
**教训：自检注入要用备份文件回滚，不要用 `git checkout` 去碰未提交的改动。**

## 七、未测（不得当成已通过）

  同类内 TTK 全落在窄带里（手枪 0.32~0.42s），差异主要来自**几枪致死 / 弹匣 / 重量 / 开镜**，
  这些必须靠试玩判定 —— 主观项不代签。
- ❌ **内容比例失衡**：武器 30 把 vs 地图 2 张 / AI 3 档 7 名。R07 的具体形态。
- ❌ AI 不使用新武器（AI 走伪武器解算，与玩家武器表无关）—— 本次只影响玩家侧。

  没有验"1~20 级解锁梯度是否合理、玩家在第 N 级买得起什么"。
- ❌ 便携版未重建（`build-portable.mjs` 属发布步骤，M6-1 不走发布）。
- ❌ 新武器未进 M6-TEMP-REGISTRY（**本次没有产生任何 `[M6-TEMP-n]` 临时实现**，
