## 一、一句话结果

配装从"多套预设"收敛成**一份当前配装**；「装备」页多出两个按钮：**「最近一局」**（一键恢复上次入局的
装备与弹药/消耗品）与**「一键补齐」**（缺件时用货币从商店买齐，二次确认并明示总价）；
旧存档迁移**清空配装**但**一件不丢**（装备与弹药都在仓库里）。

## 二、要守住的不变式（开工前先写下来，避免边写边想）

| 不变式 | 为什么必须这样 |
|---|---|
| **`stash` 与 `carry` 互不相交** | 拖入即从仓库**搬走**（`carryPlaceFromStash` 先落网格、成功了才 `stashRemove`）。顺序反了会出现"网格里有、仓库里也在"的两份 —— 这是 M6-4 已定下的口径，本批次不得退化 |
| **`lastRaid` 只记 `itemId + count + 落点`，不记 uid** | uid 是"这一件在哪"的编号；下一局仓库已经换过（上一局的被带走、新捡的进来），按 uid 恢复必然对不上 |
| **恢复优先"数量恰好"的整条，否则拆出目标数量** | 避免"为了凑 30 发把一盒 60 发拆开"的无谓碎片化；同时严格还原上次的布局与负重 |
| **补齐只走 `buyPriceOf`，且只补到上次的数量** | 价格只有一处实现；补齐不能变成"顺便多买"。未解锁的单列提示、不补、不整单拒绝 |
| **花钱必须二次确认** | 这是全项目最"危险"的一类交互（自动花玩家的钱）。弹窗要明示清单与总价；货币不足则拒绝并告知差多少 |
| **恢复/补齐之后立刻跑 `auditCarryBeforeRaid`** | 复用既有的"进局检查"判定，不另写一套；有问题就走既有的警告页 |
| **迁移留 `repairs` 痕迹 + 大厅提示一次** | 数据重置是玩家应知情的事；静默清空配装会被当成"存档坏了"。不走 `MIGRATIONS`（迁移函数会静默丢东西） |
| **`presetId` 参数一律去掉，不留兼容分支** | 留着"传什么都行"的兼容参数，旧调用会**静默**走到错的预设上 |
| **多套预设要"真被删掉"而不是"藏起来"** | 反向断言：把 `addPreset|removePreset|setActivePreset|renamePreset` 加进冒烟的静态源码禁用扫描（与 `ammoInc` 那批同级） |
