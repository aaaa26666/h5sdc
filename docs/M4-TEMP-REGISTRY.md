## 五、缺陷登记

> 格式沿用 `docs/M2-TEMP-REGISTRY.md` 三点十节与 `docs/M3-TEMP-REGISTRY.md` 第五章：
> 编号 + 分级 + 发现于 + 位置 + 现象 + 根因 + 为什么没被抓到 + 修复 + 证据链。
> 修复处的代码注释里写同一个编号，`grep -rn "M4-BUG-0" src/ tools/` 即可定位。

### 5.1 M4-BUG-01：调试接口 `killOneAi()` 从 M0~M2 起就是坏的，导致 killsAfter 撤离点零覆盖

| 项 | 内容 |
|---|---|
| 编号 | **M4-BUG-01** |
| 分级 | **S2** —— 它不影响正常玩法（接口只在开发构建存在），但它**阻断了 M4-1 一条交付内容的验收** |
| 发现于 | M4 收尾审计（对"地图表新增的条件撤离点"做端到端覆盖时） |
| 位置 | `src/main.js` 的 `killOneAi()`；`src/gameplay/ai.js` 的 `applyHitFrom`；`src/core/ballistics.js` 的 `rawZoneDamage` |

#### 现象

调用 `window.__m2.killOneAi()` 必抛：

```
Error: [ballistics] 武器 debug 未定义部位 chest 的伤害
    at rawZoneDamage (src/core/ballistics.js:24)
    at applyHitFrom (src/gameplay/ai.js:572)
```

3/3 次调用全部抛错。

#### 根因（有两层，第二层在修完第一层之后才暴露）

**第一层：假武器的形状与伤害模型不匹配。**
`ballistics.rawZoneDamage()` 取的是**按部位的对象** `weapon.damage[zone]`，
而 `killOneAi` 传的是标量：

| | 形状 |
|---|---|
| 真实武器（`weapons.json`） | `damage: { head:52, chest:30, stomach:27, limb:21 }` |
| `killOneAi` 曾经传的 | `damage: a.vitals.maxHealth * 10`（一个数） |

**第二层：击杀计数只由武器的事件路径自增。**
`combatStats.kills++` 原先只写在武器的 `hit` 事件里（`if (ev.killed) ...`），
也就是说**只有"玩家用枪打死"这条路**会记数。`killOneAi` 直接调 `applyHitFrom`，
绕过了武器 —— 于是 AI 确实死了（存活 6→5→4），但 `kills` 一直是 **0**，
而 M4-1 的 `killsAfter`（e4_archive 要求累计 3 杀）读的正是这个数，**永远开不了**。

#### 为什么此前全绿

| 断言 | 为什么是绿的 |
|---|---|
| `verify-prod-bundle.mjs` | 它只检查 `"killOneAi"` 这个字符串**有没有被打进生产包**（检查通过），**从不调用它**。于是"已注册、已列入校验名单、一调就炸"的状态挂了整整一个 M3 + M4 |
| 端到端 | 没有任何一条断言用过它（`grep -rn killOneAi tools/` 只命中 verify 的字符串表） |
| 地图校验 | `render-map` 只校验地图表内部（撤离点位置/数量），不执行开放规则 |

#### 修复

1. `killOneAi()`：假武器的 `damage` 改为按部位的对象（形状与 `weapons.json` 对齐），
   每部位取 `maxHealth × 10` 保证一次命中必定淘汰 —— 它是夹具，不该被护甲/衰减影响。
2. 新增 `syncKills()`：把 `aiManager.kills`（"谁死了"的权威）同步进 `combatStats.kills`
   （缓存），并在 `snapshot()` 与 `killOneAi()` 里各对一次。
   用 `max` 而不是覆盖 —— `aiManager.noteKill()` 在武器事件里先于死亡清扫执行，
   取 max 才能保证读数单调不倒退。
3. `killOneAi()` 里显式补 `aiManager.noteKill()`，与武器那条路径做的事完全一致。

#### 证据链

| 环节 | 证据 |
|---|---|
| 缺陷真实存在 | 修复前 3/3 次调用抛异常；即使把 AI 打死，`kills` 仍为 0（存活 6→5→4 而 kills=0,0,0） |
| 修复有效 | `killOneAi` 三次调用全部返回 true；kills 序列 **1,2,3**；e4_archive `open=true reason=killsReached`；在该点完成撤离 `reason=extracted carried=true` |
| 回归防线 | `tools/smoke.mjs` 新增「M4-BUG-01 killsAfter 撤离点（此前零覆盖）」组（6 条断言） |

#### 尚未验证

- 这条缺陷的**第二层**（计数只认武器路径）是我在修第一层时实测发现的。
  同类风险还有：任何"非武器来源的伤害/死亡"（将来的手雷、陷阱、坠落伤害）
  都必须显式接进击杀计数，否则 `killsAfter` 会再次与事实脱节。
  `syncKills()` 只兜住了"AI 已死但计数没跟上"，兜不住"死亡本身没被记为击杀"。

### 5.2 M4-BUG-02：不点提示直接开新局 = 静默丢档（含安全箱）

| 项 | 内容 |
|---|---|
| 编号 | **M4-BUG-02** |
| 分级 | **S1** —— 直接违反 M4 DoD「所有结束路径均有明确结算且**不丢档**」与风险对策「禁止在断线/刷新场景下静默丢弃玩家进度」 |
| 发现于 | M4 收尾审计（专门去测"不点提示直接开新局"这条分支 —— 既有断言只覆盖了"点提示"那条） |
| 位置 | `src/main.js` 的 `startRaid()`（无条件 `clearCheckpoint()`）与 `interruptedNotice` 点击处理器 |

#### 现象（实测）

| 步骤 | 观测 |
|---|---|
| 局内搜到 1 件（保险箱 90），等定期快照 | localStorage 快照 248 字节 |
| 强行刷新 → 重进 | "上局未正常结束"提示可见 ✓ |
| **不点提示**，直接点"进入战区" | 快照被清除、`raidResult` 为 null —— 上局**没有任何结算记录** |
| 后果 | 连**安全箱里本该保住的 90** 也没了。这比文档口径（断线 = 未撤离 = 保安全箱）**更差** |

#### 根因

"清快照"发生在 `startRaid()` 里（无条件），而"补结算"只挂在**点击提示**的处理器上。
两者顺序反了：先清后算，等于什么都没算。玩家不点提示是**完全合理**的操作
（他只想开下一局），不该因此丢掉上一局。

#### 修复

1. 抽出 `settleInterruptedRaid()`：读快照 → 产出结算 → 记 `lastRaidResult` → 清快照 →
   收起提示。**清快照必须在结算之后**，这是幂等的第一道防线。
2. `btnStart` 的处理里**先调它**，再 `startRaid()`；若有补结算则照常显示在结算页上。
   提示因此只承担"告知"职责，不再是结算的唯一触发点。
3. `interruptedNotice` 点击处理器改为调用同一个函数（两条路径共用一份逻辑）。
4. 顺带修掉同一族的第二个丢档窗口：**开局立刻写第一笔快照**。
   原先只有"每 5 秒一次"与"关闭瞬间一次"，开局后 5 秒内被强杀（进程被 kill 时
   `pagehide` 不保证触发）**没有任何快照**，那一局等于从未存在过。
   同时重置 `checkpointLastWrite` —— 它是跨局残留的模块级变量。

#### 证据链

| 环节 | 证据 |
|---|---|
| 缺陷真实存在 | 修复前：不点提示直接开新局 → 快照 null、`raidResult` null（背包 1 件、保险箱 90 全丢） |
| 修复有效 | 不点提示直接开新局 → `reason=disconnected`、`carried=false`、`keptValue=90`（与"点提示"路径**分毫不差**） |
| 第二面 | 新局开局 <5 秒即有快照（`elapsedMs=0 / items=0`）；开局瞬间刷新会被认成"未撤离"而不是从未存在 |
| 幂等 | 补结算后 raidId 换成新局的（证明旧快照确已被清除）；正式结算后再刷新不再提示 |
| 回归防线 | `tools/smoke.mjs` 新增「M4-BUG-02 不点提示直接开新局（此前会静默丢档）」组（5 条断言） |

#### 尚未验证

- 补结算发生时玩家**看不到结算页**（因为新局立刻开始）。数据没丢、`lastRaidResult`
  里也有，但"玩家是否会因此困惑"没有试玩结论。若要更显眼，可考虑在开局 toast 里
  提一句"上局已按未撤离结算"。
- `startRaid()` 仍保留那句 `clearCheckpoint()`（DEV 接口直接调它时不补结算）。
  这是**有意保留**的兜底，不是遗漏：正常玩家的唯一入口是 `btnStart`，
  而它已经先调 `settleInterruptedRaid()` 了 —— 这一点由代码注释与
  smoke 的「不点提示直接开新局」组同时钉住。
