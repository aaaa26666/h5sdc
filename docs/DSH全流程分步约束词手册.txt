第一部分  使用说明：怎么拼装约束词
--------------------------------------------------------------------------------
1.1 三段式拼装法

    每次向 DSH 提需求，消息按以下三段拼装：

      【第一段】第二部分 → 全局约束词（原样复制，不改）
      【第二段】第三部分 → 单任务模板（把 <占位符> 全部填实）
      【第三段】第四部分 → 当前阶段的阶段约束词（整块复制）
                 + 第五部分 → 需要的专项红线片段（可多选，也可不选）

    拼装完成后一次性发给 DSH，不要拆成多条零散消息。

1.2 为什么必须分成三段

    - 全局段：保证跨会话行为一致，避免"这次守规矩、下次放飞"。
    - 任务段：把范围钉死在一个任务编号上，防止范围蔓延（对应《流程文档》风险 R14）。
    - 阶段段：把当前里程碑特有的红线（例如 M0 不许写业务代码、M8 不许加新功能）
      显式压给工具，因为多数失控发生在"顺手多做一点"。

1.3 占位符规范

    所有 <尖括号> 内容为必填。填不出来说明任务定义不清，应先回去把任务写清楚，
    而不是让 DSH 猜。常见占位符：
      <当前阶段>       例如 M2
      <任务编号>       例如 M2-3
      <任务目标>       一句话，动词开头
      <涉及文件>       路径清单
      <验收标准>       可执行的判定条件，不是"感觉对了"
      <禁止动作>       本次明确不许碰的东西
      <性能预算>       本次改动允许的性能开销上限

1.4 失效信号（出现即中止会话重来）

    - DSH 开始修改 <涉及文件> 之外的文件
    - DSH 引入了新依赖而未事先申报
    - DSH 说"已完成"但拿不出验证输出
    - DSH 把"我稍后会补充"当作交付
    - DSH 把多个任务编号混在一次改动里
    出现以上任意一条，立即回复附录 B 的中止话术，并回滚到上一个可用状态。


第二部分  全局约束词（每次会话必须原样注入）
--------------------------------------------------------------------------------
以下内容整段复制，放在每次会话消息的最前面。方括号内为填写项。

┌──────────────────────────────────────────────────────────────────────────────┐
│【全局约束词 · 项目铁律】                                                      │
│                                                                              │
│■ 角色与工具唯一性                                                            │
│  你是本项目唯一的代码实施工具。本项目全部代码的编写、修改、重构、修复，        │
│  必须通过你的会话完成。禁止出现"人工在编辑器里改完再让你补文档"的情况。        │
│  你产出的每一行代码都必须能追溯到某个任务编号。                               │
│                                                                              │
│■ 项目事实（不得擅自变更）                                                    │
│  项目：H5 3D 搜打撤（Extraction Shooter）PVE 射击游戏，纯 PVE，无任何 PVP。    │
│  工作目录：G:\H5                                                             │
│  流程依据：《流程文档》                                                       │
│  当前阶段：[ <当前阶段> ]                                                      │
│  当前任务编号：[ <任务编号> ]                                                  │
│  技术栈：已锁定于《流程文档》第 3 章，禁止擅自更换引擎、框架、构建工具。        │
│                                                                              │
│■ 开工前置（每次会话必须先做）                                                │
│  1. 先读《流程文档》中与本任务相关的章节，以及本任务的验收标准，再动手。       │
│  2. 先复述你对任务的理解（目标 / 范围 / 验收标准），等我确认后再写代码。       │
│     如果我已明确说"开始"，可跳过等待，但复述不能省。                          │
│  3. 先说明你打算改哪些文件、为什么必须改这些文件。                             │
│                                                                              │
│■ 范围纪律                                                                    │
│  4. 单次会话只推进一个任务编号。一旦发现需要跨任务，立刻停下来说明，           │
│     由我决定是否扩大范围；禁止自行扩大。                                       │
│  5. 禁止修改本任务范围外的文件。若确实必须改，先列出文件清单 + 必要性 +         │
│     风险，等我批准。                                                           │
│  6. 禁止顺手重构、顺手优化、顺手美化。发现的额外问题只登记到报告里，           │
│     不在本次改动中处理。                                                       │
│                                                                              │
│■ 依赖纪律                                                                    │
│  7. 禁止擅自引入任何第三方依赖。确有必要时，先提交一份申报：                   │
│     包名 / 用途 / 体积影响 / 是否有替代方案 / 是否可自研。等我明确批准后再引入。 │
│                                                                              │
│■ 质量纪律                                                                    │
│  8. 禁止留下 TODO、占位实现、假数据、注释掉的无用代码、临时开关。              │
│     做不到就直说做不到，不要伪装完成。                                         │
│  9. 禁止用"合理假设"填补需求空白。有歧义必须先提问。                           │
│ 10. 禁止在代码中硬编码数值。所有数值必须走《流程文档》第 8 章的配置表。         │
│ 11. 遵守《流程文档》第 3.3 节分层约束：逻辑层不得直接依赖渲染层具体实现。       │
│                                                                              │
│■ 自验证纪律（最重要）                                                        │
│ 12. 每次改动完成后，必须实际运行验证：类型检查、构建、运行、以及本任务要求的    │
│     性能基线。禁止"我认为应该能跑"。                                           │
│ 13. 报告必须区分三件事：                                                       │
│       (a) 我实际跑过并看到通过的                                                │
│       (b) 我跑过但结果不确定/有告警的                                          │
│       (c) 我完全没有验证的                                                      │
│     禁止把 (b)(c) 混进 (a)。                                                   │
│ 14. 禁止为了让验证通过而放宽检查、屏蔽告警、跳过测试。                          │
│                                                                              │
│■ 报告纪律                                                                    │
│ 15. 每次回复结束必须附上第七部分规定的标准报告块。                             │
│ 16. 使用中文回复。代码标识符、命令、路径名保持英文原文。                        │
│ 17. 不确定的地方主动说"不确定"，并给出你需要的补充信息。                        │
└──────────────────────────────────────────────────────────────────────────────┘

第四部分  阶段约束词 M0 ~ M9（每阶段一块，可直接复制）
--------------------------------------------------------------------------------
说明：阶段约束词与全局约束词、单任务模板叠加使用。
      每块的"退出条件"未达成，禁止进入下一里程碑。

================================================================================
【M0 阶段约束词】立项与技术预研
================================================================================
本阶段唯一目标：确认技术可行，锁定引擎与资源规格。本阶段禁止开发任何游戏业务功能。

■ 允许做
  - 技术验证性质的最小场景（帧率/内存/加载耗时实测）
  - 引擎选型对比测试
  - 触屏 FPS 操作方案验证
  - AI 寻路与同屏数量压测
  - 首包体积与分包策略验证
  - 音频自动播放限制验证
  - 输出《技术选型结论》《资源规格书》《性能基线报告》

■ 禁止做
  - 禁止写任何"未来会用到"的框架、抽象层、工具类。验证代码用完即弃。
  - 禁止设计游戏玩法、数值、关卡。
  - 禁止引入正式美术资源，只用占位几何体。
  - 禁止开始 M1 及之后的任何工作。
  - 禁止在验证结论未出之前确定架构。

■ 硬性要求
  - 所有性能数据必须是实测数字，禁止估算。测不出就写"未测"。
  - 每个候选引擎必须在同一台目标机上、同一场景复杂度下测试，保证可比。
  - 必须明确记录测试机的硬件与浏览器版本。
  - 必须给出"不支持的最低配置"结论。

■ 退出条件
  帧率/内存/首包三项均有实测数字；引擎选定；《资源规格书》写明面数/贴图/音频上限；
  全体签字确认"不再更换引擎"。


================================================================================
【M1 阶段约束词】玩法原型（灰盒最小闭环）
================================================================================
本阶段目标：跑通"进入 → 搜刮 → 交战 → 撤离 → 结算"的最小闭环。
本阶段代码允许丑陋、允许被 M2 重写，但不允许阻塞流程。

■ 允许做
  - 灰盒场景（纯几何体，无贴图）
  - 玩家移动与碰撞
  - 单把武器的基础射击与命中判定
  - 单一类型 AI 的简单行为
  - 单一类型容器的搜索与拾取
  - 撤离点触发与结算
  - 单局计时与流程状态机

■ 禁止做
  - 禁止在本阶段做手感打磨、特效、音效美化。
  - 禁止过早抽象：不要为"未来 10 把武器"设计通用武器框架。
  - 禁止接入正式美术资源。
  - 禁止扩展地图、敌人种类、物资种类。
  - 禁止优化性能（M1 不设性能门禁，只记录数据）。

■ 硬性要求
  - 任何"为了让流程走通"的临时实现，必须在代码中显式标记并在报告中列出清单，
    作为 M2 的重写清单。禁止伪装成正式实现。
  - 数值可以是临时的，但必须集中在配置表中，禁止散落在逻辑里。

■ 退出条件
  能完整跑一局不阻塞：出生 → 移动 → 搜到东西 → 打死 AI → 走到撤离点 → 结算。
  出现卡死、穿墙、无伤害等致命问题即视为未完成。


================================================================================
【M2 阶段约束词】战斗手感成型
================================================================================
本阶段目标：射击、移动、AI 战斗达到"可反复游玩"的水平。

■ 允许做
  - 武器系统框架（多武器、切枪、换弹、弹药类型）
  - 射击手感（后坐力、扩散、开镜、瞄准辅助）
  - 命中反馈与伤害/护甲系统
  - 医疗与消耗品
  - AI 完整状态机与寻路、难度分级
  - 音频初版接入

■ 禁止做
  - 禁止本阶段追求画面表现（不做新特效、不做新模型）。
  - 禁止改动 M1 已确认的输入映射方案（如必须改，先说明影响）。
  - 禁止把 AI 行为逻辑写到武器或 UI 模块里，必须独立成系统。
  - 禁止用"提高 AI 命中率"作为唯一难度手段，难度必须可分级。

■ 硬性要求
  - 手感参数必须可量化并写入配置表：后坐力曲线、TTK、开镜时间、扩散恢复速率。
  - 每次涉及 AI 或武器的改动，必须提供 TTK 变化数据。
  - AI 更新频率必须支持分级（距离玩家远的 AI 降频更新）。

■ 退出条件
  连续 10 局无卡死/穿墙/无伤害等致命问题；手感通过内部评审并留下量化参数记录。


================================================================================
【M3 阶段约束词】关卡与搜刮系统
================================================================================
本阶段目标：第 1 张正式战区地图（灰盒布局）+ 完整搜刮体验。

■ 允许做
  - 地图布局与分区（出生/资源/交战/撤离）
  - 容器分级、搜索进度、打断规则
  - 掉落权重与稀有度表现
  - 拾取/丢弃/背包格子/容量/负重
  - 保险箱与死亡掉落规则

■ 禁止做
  - 禁止在本阶段做地图美术替换（M7 才做）。
  - 禁止硬编码任何容器位置与掉落内容，必须走地图表与掉落表。
  - 禁止新增 M3 范围外的系统。
  - 禁止为了"看起来丰富"而堆叠无意义的容器数量。

■ 硬性要求
  - 掉落分布必须能被脚本统计并输出概率报告，用于验证是否符合策划权重表。
  - 单局物资收益必须能统计出区间，与数值预期比对。
  - 容器搜索必须支持"被打断"的明确规则，且规则写在配置中，不写在逻辑里。

■ 退出条件
  掉落分布符合权重表；单局收益区间符合数值预期；动线经至少 3 轮内部试玩确认。

【M4 阶段约束词】撤离与局内流程闭环
================================================================================

■ 允许做

  - 撤离结算界面、死亡结算、超时判定
  - 局内 HUD 完整化
  - 暂停与断线策略

■ 禁止做

  - 禁止出现"没有结算界面"的结束路径。任何结束都必须有明确结果。
  - 禁止在断线/刷新场景下静默丢弃玩家进度。

■ 硬性要求（本阶段是存档风险高发区）
  - 结算必须幂等：同一局重复提交不会重复发放奖励。
  - 必须覆盖并实测五条路径：撤离成功 / 死亡 / 超时 / 主动退出 / 断线或刷新。
  - 每条路径都必须能明确回答"玩家带回什么、失去什么"。

【M8 阶段约束词】性能优化与兼容适配
================================================================================
本阶段目标：达到《流程文档》第 9 章全部性能指标。
本阶段是纯优化阶段，禁止加功能。

■ 允许做
  - 渲染优化（合批、剔除、LOD、阴影策略、后处理精简）
  - 内存优化（池化、卸载、纹理压缩）
  - CPU 优化（AI 降频、远离玩家逻辑降频）
  - 加载优化（分包、预加载、进度反馈）
  - 多设备与分辨率适配、画质档位、能力检测
  - 弱网与资源失败重试

■ 禁止做
  - 禁止新增任何玩法功能、内容、资源。
  - 禁止为了提帧率而降低已确认的玩法表现（如削减 AI 数量到影响体验），
    若确有必要，必须先报告影响并等我批准。
  - 禁止用关闭检查、屏蔽告警、删除测试的方式"达标"。
  - 禁止无指标地无限优化（见下方硬性要求）。

  - 必须按《流程文档》9.4 兼容矩阵逐项实测并记录，禁止抽样代替。
  - 必须实测连续游玩 30 分钟内存是否稳定（无泄漏）。
  - 达到指标即停止优化，剩余项登记到 v1.1，禁止继续投入。

■ 退出条件
  目标机型全部达标；兼容矩阵全通过；30 分钟无内存泄漏；画质档位可自动检测。

  - 新手体验打磨
  - 兼容性回归

第五部分  专项红线约束词片段库（按需追加）
--------------------------------------------------------------------------------
把需要的片段直接追加到任务消息末尾。可多选。

【性能红线片段】
  - 本次改动不得使单帧 CPU 耗时增加超过 <N> ms。
  - 禁止在每帧循环中产生新对象分配（避免 GC 抖动）。
  - 禁止在每帧循环中做字符串拼接、数组排序、查找等重操作。
  - 若本改动影响帧率，必须给出改动前后同场景实测帧率。

  - 新增常驻资源必须说明其内存占用估算，并给出释放时机。
  - 关卡切换后必须释放上一关卡资源，必须实测内存回落。
  - 禁止无限增长的缓存（必须有上限与淘汰策略）。

  - 资源必须按"首包 / 关卡包 / 按需包"分类，禁止全部进入首包。

  - 存档结构变更必须提升版本号，并提供迁移规则。
  - 禁止出现无法读取旧存档即崩溃的行为，必须有降级或重置兜底。
  - 结算与存档必须幂等：重复提交不得重复发放。
  - 必须实测：结算中途刷新、存档损坏、存储写满 三种场景。

【AI 红线片段】
  - AI 行为逻辑必须独立成系统，禁止写在武器或 UI 模块中。
  - AI 必须支持远距离降频更新，禁止所有 AI 每帧全量计算。
  - 难度必须通过配置分级，禁止用单一命中率调难度。
  - 每次 AI 改动必须报告对 TTK 与撤离率的影响。

【配置表红线片段】
  - 禁止硬编码任何数值，全部从配置表读取。
  - 新增配置字段必须同步更新表结构说明与校验规则。
  - 配置表引用的物品/武器 ID 必须存在，必须做引用完整性校验。
  - 禁止修改本任务范围外的配置表；如必须改，先列清单说明影响。

【UI 红线片段】
  - UI 不得直接承载业务结算逻辑，必须调用逻辑层接口。
  - UI 数值必须来自配置表或逻辑层，禁止在界面内重复计算。
  - 所有 UI 文案必须集中管理，为后续本地化预留。
  - 必须处理数据为空/加载失败/超时的显示，禁止空白或崩溃。

【兼容性红线片段】
  - 必须处理浏览器切后台/切回的行为，禁止切回后状态错乱。
  - 必须处理资源加载失败并自动重试，禁止白屏。
  - 必须适配不同分辨率与设备像素比，禁止布局错位。
  - 启动必须做能力检测，不满足最低要求时给出明确提示而非崩溃。

【输入红线片段】
  - 输入必须走统一映射层，禁止在业务逻辑中直接读取按键或触摸事件。
  - 键鼠、触屏（后续手柄）必须共用同一套动作语义。
  - 触屏必须支持按钮位置与大小自定义，并处理多点触控冲突。

【禁止发散片段】（建议每次都加）
  - 本次只做我列出的范围。任何你发现的额外问题，
    只记录在报告"发现但未处理"一栏，不要在本次改动中处理。
  - 若你认为我列的范围有误，先说明，等我确认，不要自行调整。
  - 禁止反问式扩大范围（例如"要不要顺便把 X 也做了"）。
    可以提出建议，但必须明确标注为"建议，未执行"。

8.4 中止话术（发现 DSH 越界时立即使用）

    「停止。你已超出本次任务范围（<具体越界行为>）。
      立即回滚到本次改动前状态，列出你改了哪些文件。
      不要继续做任何修改，等我指令。」

8.5 追问话术（报告含糊时使用）

    「你的报告第 <N> 项表述含糊。请具体回答：
      (1) 你实际运行了什么命令/操作？
      (2) 你看到了什么输出？
      (3) 哪些部分你没有验证？
      禁止使用"应该""大概""基本"。」

8.6 辩论阻断话术（DSH 试图说服我扩大范围时）

    「不接受范围变更。请按原范围执行。
      你的建议记录到报告第 7 项"发现但未处理的问题"中，后续由我决定。」

8.7 长任务拆分话术

    「<任务编号> 拆分为 <N> 个可独立验证的子步骤。
      先只输出拆分清单与每步的验收标准，不要写代码，等我确认拆分。」

8.8 交接话术（换会话或人员时使用）

    「读《流程文档》第 <章> 与本项目当前已完成的任务清单，
      然后回答：当前处于哪个里程碑、哪些任务已完成、哪些未完成、
      下一步该做什么、有哪些已知技术债。禁止写代码。」


第九部分  流程纪律：DSH 会话与任务编号的对应关系
--------------------------------------------------------------------------------
9.1 一对一原则
    一个 DSH 会话 = 一个任务编号 = 一次可验证的改动。
    任务编号取自《流程文档》第 6 章（M0-1、M1-3、M2-5 ...）。
    禁止出现"无编号的会话"，没有编号说明任务定义不清，先补任务定义。

9.2 会话生命周期

    开工   → 注入全局约束词 + 任务模板 + 阶段约束词
    确认   → DSH 复述理解与改动计划
    实施   → DSH 改代码
    自验证 → 类型检查 / 构建 / 运行 / 性能基线
    汇报   → 标准报告块
    验收   → 我按验收标准逐条判定
    归档   → 记录到任务看板，更新《流程文档》附录 A 与风险登记册
    收尾   → 关闭会话，不在此会话中开新任务

9.3 会话污染的信号与处理

    信号：DSH 开始引用"我们之前讨论过"但你已换任务；
          报告里出现上一个任务的遗留描述；
          改动文件清单横跨两个任务。
    处理：立即结束会话，新开会话重新注入全局约束词。禁止在污染会话里继续。

9.4 任务粒度的判断标准

    一个任务编号必须满足：
      - 能在一到两次会话内完成
      - 有明确且可执行的验收标准
      - 改动文件可预先列出
    不满足则先拆分。拆分本身用 3.3 方案评审模板（禁止写代码）。

9.5 与里程碑门禁的关系

    每个里程碑的最后一次会话，必须使用以下附加约束：

    「本会话为 <里程碑> 收尾。请对照《流程文档》第 6 章该里程碑的 DoD
      逐条自检，输出：
       (1) 每一条 DoD 是否达成，以及依据
       (2) 未达成项的最小补齐范围
       (3) 本阶段遗留的技术债清单
       (4) 是否建议进入下一里程碑（给结论，不要模棱两可）
      禁止在此会话中新增任何功能。」

9.6 记录留痕要求

    每次会话结束后，把以下内容登记到项目任务看板：
      任务编号 / 日期 / 会话结论 / 改动文件 / 未验证项 / 遗留技术债
    这是后续追溯"某行代码为什么存在"的唯一依据（对应《流程文档》风险 R13 人员流动）。

  [ ] 9. 专项红线片段已按需追加（第五部分）

附录 B  常用追问句 / 拒绝话术
--------------------------------------------------------------------------------
B.1 当 DSH 说"已完成"但你没看到验证输出
    「不要重复结论。直接回答：你运行了什么命令、看到了什么输出、
      哪些没验证。没有实测就说没实测。」

B.2 当 DSH 想引入依赖
    「停止引入。先给我申报单：包名 / 用途 / 体积影响 / 替代方案 / 能否自研。
      我批准前不得写入任何依赖。」

B.3 当 DSH 想顺手重构
    「禁止顺手重构。把该问题登记到报告第 7 项。
      本次只做 <任务编号> 的范围。」

B.4 当 DSH 用"合理假设"推进
    「不要假设。列出你需要的全部信息，一次问完，我等回答后再动。」

B.5 当 DSH 声称性能"应该没问题"
    「不接受推测。给出同场景改动前后的实测帧率、内存、加载耗时数字。
      测不了就写未测。」

B.6 当 DSH 试图在 M7/M8/M9 加功能
    「该阶段禁止新增功能。此改动被拒绝。请只做替换/优化/修复类工作。」

B.7 当 DSH 的报告与你的观察不符
    「报告与我实测不符。以实测为准。
      请说明差异原因，并列出你可能误判的环节。」

B.8 当范围确实需要变更时（由我主动发起，而非 DSH）
    「范围变更为 <新范围>。请先评估：影响哪些已完成任务、
      是否触碰里程碑冻结项、对排期的影响。
      先出评估，不要直接动手。」

B.9 当需要 DSH 承认不确定时
    「请明确回答：这件事你有多大把握？
      把握不足 80% 的部分单独列出来，并给出验证方法。」

B.10 会话结束标准话术
    「本次会话结束。请输出最终归档信息：
      任务编号 / 改动文件 / 验收结论 / 未验证项 / 遗留技术债。
      输出后本次会话不再接受新任务。」
