第 1 章  项目定位与核心目标
--------------------------------------------------------------------------------
1.1 一句话定位
    一款可在浏览器直接打开、无需下载客户端的 3D 第一人称搜打撤射击游戏，
    玩家进入战区搜刮物资、与 AI 敌人交战、并在限定时间内赶到撤离点安全撤离，
    成功撤离后把战利品带回仓库用于长期养成。

1.2 目标用户
    - 喜欢《逃离塔科夫》《三角洲行动》式"高风险高回报"循环，但不想下载大客户端的玩家。
    - 碎片化时间玩家：单局 8~15 分钟，可随时中断（中断判定见 2.6）。
    - 低配设备用户：集成显卡笔记本、中低端手机浏览器。

1.3 核心体验目标（三者必须同时成立）
    (1) 紧张感：死亡即失去本局携带物，撤离才有收益。
    (2) 成长感：仓库、装备、等级、任务线带来长期追求。
    (3) 可上手：H5 端操作门槛低，新手 3 分钟内理解"进去—搜刮—撤离"。

1.4 成功判据（可量化）
    - 首次进入游戏到完成第一局撤离：<= 8 分钟。
    - 低配目标机（集显 + 4GB 可用显存）平均帧率 >= 30 FPS。
    - 单局加载时间（首包已缓存）<= 6 秒。
    - 首包体积（首次加载必要资源）<= 30 MB（建议 15~25 MB）。
    - 单局平均时长 8~15 分钟，撤离率目标区间 45%~65%（可调）。

1.5 明确的非目标（本期不做）
    - 不做 PVP、不做联机对战、不做真人组队（后续版本再评估）。
    - 不做开放世界大地图，只做单张或多张"小战区"关卡。
    - 不做写实级画质，走"低多边形 + 强风格化"路线以适配 H5。
    - 不做复杂载具系统、不做建造系统。
    - 不做内购与商业化系统（本期只做玩法闭环）。


第 2 章  玩法设计基线（搜 / 打 / 撤）
--------------------------------------------------------------------------------
2.1 核心循环（单局）
    准备(仓库配装) -> 匹配(PVE 无匹配，直接进图) -> 进入战区 ->
    搜刮物资 -> 遭遇 AI 战斗 -> 抉择(继续贪 / 立即撤) -> 到达撤离点 -> 撤离结算 ->
    仓库整理与养成 -> 再次准备

2.2 "搜"（Loot）设计要点
    - 容器分级：普通箱 / 军用箱 / 保险箱 / 钥匙房。等级越高，价值越高，搜索耗时越长。
    - 搜索为"进度条 + 可被打断"机制，被打断则进度部分保留或清零（需在策划案中定死）。
    - 物资分类：武器、弹药、护甲、医疗、消耗品、任务物品、纯价值物品（垃圾/贵重）。
    - 稀有度：白 / 绿 / 蓝 / 紫 / 金 五档，决定掉落权重与视觉表现（光束、音效）。
    - 单局物资总量与刷新规则必须表驱动，禁止硬编码（见第 8 章）。

2.3 "打"（Combat）设计要点
    - 战斗对象：AI 敌人（多档难度）、环境威胁（可选）、AI 精英/Boss（可选后置）。
    - AI 分级：
        · 巡逻兵：固定路线，视野短，反应慢。
        · 守卫兵：驻守要点，会追击但不跨区。
        · 精英兵：会侧移、会找掩体、会投掷物。
        · Boss：单局 1 名，高血量高掉落，仅在高级战区出现。
    - AI 必须具备：感知（视锥+听觉）、状态机（巡逻/警觉/交战/搜索/撤退）、寻路、射击精度分级。
    - 武器手感关键项：后坐力、开镜、扩散、命中反馈、爆头判定、换弹、切枪。
    - 护甲与部位：头/胸/腹/四肢分区伤害，护甲减伤与耐久消耗。
    - 死亡处理：玩家死亡 = 本局失败，身上携带物全部损失（保险箱内物品可保留，需策划确认）。

2.4 "撤"（Extraction）设计要点
    - 撤离点：单局 2~4 个，分为常驻点与条件点（如需要特定钥匙、特定时间后开放）。
    - 撤离流程：进入区域 -> 倒计时（如 10 秒）-> 期间不可离开区域否则重置 -> 成功撤离。
    - 时间压力：单局总时限（如 15 分钟），超时判定失败。
    - 撤离结算界面：本局收益、经验、任务进度、存活/击杀数据。

2.5 长期养成（局外）
    - 仓库系统：格子容量限制、堆叠规则、快速出售。
    - 角色成长：等级、技能树（如耐力、负重、搜索速度、后坐力控制）。
    - 任务线：商人委托（收集类 / 击杀类 / 撤离类），完成后解锁新装备与地图。
    - 经济：货币、买入/卖出价差、装备价值分级（决定进图风险）。

2.6 难度曲线与新手保护
    - 新手前 3 局：AI 数量与精度下调，地图引导强化，撤离点高亮。
    - 动态难度（可选）：根据玩家近期撤离率微调 AI 强度，需在策划案中设定上下限。
    - 断线/关闭浏览器：视为"未撤离"，需明确惩罚规则并在首次进入时告知玩家。

2.7 需要产出的策划文档清单
    - 核心循环与数值框架案
    - 地图与关卡设计案（每张图一份）
    - 武器与配件数值表
    - 物资与掉落权重表
    - AI 行为与难度曲线案
    - 经济系统与商人案
    - UI/UX 流程图（大厅、仓库、配装、局内 HUD、结算）


第 3 章  技术选型与架构规划
--------------------------------------------------------------------------------
3.1 渲染方案选型（必须早定，影响全项目）
    候选：
      A. Three.js          —— 生态大、资料多、可控性强，需自建大量系统。
      B. Babylon.js        —— 内置物理/动画/编辑器能力更全，包体略大。
      C. PlayCanvas        —— 引擎+编辑器一体化，团队协作友好，但定制受限。
    决策原则：
      - 具备自研能力、追求体积与性能极致 -> 选 A。
      - 追求开发速度、需要现成工具链 -> 选 B。
      - 需要在线编辑器与美术协作流水线 -> 选 C。
    结论建议：H5 3D FPS 项目推荐 B 或 A；本文件默认以"可自研 + 可控包体"为前提，
    在第 5 章 M0 阶段通过技术验证 Demo 后正式锁定，锁定后不再更换。

3.2 前后端与资源
    - 客户端框架：轻量级 UI 框架（或原生 DOM/Canvas 覆盖层）+ 3D 引擎。
    - 语言与构建：TypeScript + 现代构建工具，产物需支持按需分包（首包 / 关卡包 / 模型包）。
    - 资源格式：模型走压缩格式（如 glTF 衍生压缩），贴图走压缩纹理（含移动端格式回退）。
    - 后端（轻量）：账号、存档、仓库数据、任务进度、排行榜（可选）。
    - 通信：HTTP 用于局外数据，WebSocket 可选（若未来加联机则预留接口层）。
    - 部署：静态资源走 CDN，注意 CDN 缓存策略与版本号刷新。

3.3 架构分层（逻辑规划，不涉及实现）
    表现层   ：渲染、动画、特效、音频、UI
    逻辑层   ：游戏循环、状态机、战斗、AI、搜刮、撤离、关卡流程
    数据层   ：配置表加载、存档读写、资源清单
    平台层   ：输入（键鼠/触屏/手柄）、存储、网络、设备能力探测
    约束：逻辑层禁止直接依赖渲染层，便于后续加联机或做单机回放。

3.4 关键技术验证点（必须在 M0 完成）
    - WebGL 在目标机型上的稳定帧率与内存占用实测。
    - 移动端触屏 FPS 操作是否可行（双摇杆 + 自动开火 / 简易瞄准）。
    - AI 数量上限压测：同屏 N 个 AI 时的帧率与 CPU 占用（N 需实测确定）。
    - 首包体积与分包加载策略可行性。
    - 音频在移动浏览器上的自动播放限制处理方案。
    - 浏览器切后台 / 断线 / 刷新 的行为与数据安全策略。

3.5 版本与工程规范
    - 分支策略：主干 + 功能分支 + 里程碑标签。
    - 提交规范：类型(范围): 描述，必须关联任务编号。
    - 代码评审：所有合入主干的改动至少 1 人评审。
    - 自动化：构建、类型检查、静态检查、单测纳入流水线。
    - 本阶段仅规范，不产出代码。


第 4 章  美术与音频资源管线
--------------------------------------------------------------------------------
4.1 美术风格基线
    - 风格：低多边形 / 中低精度写实，强调轮廓与光照氛围，弱化贴图细节。
    - 优势：包体小、性能好、风格统一成本低。
    - 色彩：战区地面灰绿褐，物资与高价值物品用高饱和色 + 发光做视觉引导。

4.2 资源规格约束（必须写成规格书交给外包/美术）
    - 单个角色模型面数上限、骨骼数量上限、贴图尺寸上限。
    - 场景模块化：墙体/地板/掩体统一网格尺寸，便于拼装与合批。
    - 贴图统一走图集或压缩纹理，禁止大量独立小贴图。
    - 特效使用粒子与贴图序列帧，限制同屏粒子总数。
    - 所有资源命名规范、目录规范、版本号规范。

4.3 资源清单（示例结构，具体条目由美术在 M1 输出）
    - 角色：玩家手臂（第一人称）、AI 若干兵种。
    - 武器：本期建议 6~10 把（手枪/冲锋枪/步枪/霰弹/狙击/近战）。
    - 场景：1~2 张战区地图的模块化组件 + 道具 + 容器。
    - UI：图标、按钮、面板、准星、状态条。
    - 特效：枪口火焰、弹壳、弹孔、命中、爆炸、烟雾、搜索高光。
    - 音频：枪声（每枪种开火/远距离/换弹/空仓）、脚步、环境音、UI 音、BGM。

4.4 音频规范
    - 采样率与位深统一（按移动端兼容性最优选择）。
    - 短音效走压缩格式，BGM 长音频单独按需加载。
    - 必须有距离衰减与遮挡处理，枪声远近差异是沉浸感核心。
    - 处理移动端首次交互后才能播放音频的限制。

4.5 资源交付与验收流程
    美术产出 -> 规格自检 -> 技术接入 -> 性能实测（面数/内存/加载耗时）-> 验收通过入库
    未通过规格自检的资源一律退回，不允许"先接进去再优化"。


第 5 章  研发阶段与里程碑总览
--------------------------------------------------------------------------------
阶段划分（10 个里程碑，M0~M9）：

  M0  立项与技术预研      目标：确认技术可行，锁定引擎与规格
  M1  玩法原型（灰盒）    目标：跑通"搜-打-撤"最小闭环
  M2  战斗手感成型        目标：射击/移动/AI 基础战斗可用
  M3  关卡与搜刮系统      目标：1 张完整战区地图 + 完整搜刮流程
  M4  撤离与局内流程闭环  目标：一局游戏可从进入到结算完整跑通
  M5  局外系统（大厅/仓库/配装/养成）
  M6  内容扩充            目标：武器、AI、物资、地图扩充到可玩体量
  M7  美术与音频替换      目标：灰盒资源全部替换为正式资源
  M8  性能优化与兼容适配  目标：达到第 9 章性能指标
  M9  测试打磨与上线      目标：缺陷收敛 + 发布

里程碑硬性规则：
  - 每个里程碑有明确的"完成定义（DoD）"，未达 DoD 不得进入下一阶段。
  - 每个里程碑结束产出：可运行版本 + 验收记录 + 文档更新 + 风险更新。
  - 每个里程碑建议时长见第 13 章，允许 ±20% 浮动，超出即触发范围重议。


第 6 章  各阶段详细任务分解（M0 ~ M9）
--------------------------------------------------------------------------------
【M0】立项与技术预研                                      建议周期：2~3 周
  任务：
    M0-1 确认玩法定位、目标平台、性能目标（本文件第 1、9 章）
    M0-2 渲染引擎三选一的技术验证（各做一个小场景跑帧率与内存）
    M0-3 移动端触屏 FPS 操作方案验证
    M0-4 AI 寻路与同屏数量压测
    M0-5 首包体积/分包策略验证
    M0-6 输出《技术选型结论》与《资源规格书》
  交付物：技术验证 Demo（可丢弃）、选型结论文档、资源规格书、性能基线报告
  DoD：目标机帧率与内存数据实测达标；引擎选定且全体签字；规格书写明数值上限
  风险：选型反复。对策——一次性评估，签字后不再更换。

【M1】玩法原型（灰盒最小闭环）                           建议周期：3~4 周
  任务：
    M1-1 灰盒场景（白色方块地图，含掩体、容器、撤离点）
    M1-2 玩家移动（走/跑/蹲/跳/趴）、碰撞与重力
    M1-3 基础射击（单武器、命中判定、伤害）
    M1-4 1 个最简 AI（站桩 + 简单追击 + 射击）
    M1-5 容器搜索与拾取
    M1-6 撤离点触发与成功结算
    M1-7 单局流程与计时
  交付物：可完整跑一局的灰盒版本
  DoD：从出生到撤离全程无阻塞；能搜到东西、能打死 AI、能成功撤离
  风险：闭环时间超预期。对策——M1 只做 1 把武器、1 种 AI、1 个容器类型。

【M2】战斗手感成型                                      建议周期：4~6 周
  任务：
    M2-1 武器系统框架（多武器、切枪、换弹、弹药类型）
    M2-2 射击手感（后坐力、扩散、开镜/腰射、瞄准辅助）
    M2-3 命中反馈（弹孔、命中音、受击提示、击杀提示）
    M2-4 伤害与护甲系统（部位伤害、护甲耐久）
    M2-5 医疗与消耗品使用
    M2-6 AI 完整状态机（巡逻/警觉/交战/搜索/撤退）+ 寻路
    M2-7 AI 难度分级与刷新规则
    M2-8 音频初版接入（枪声、脚步）
  交付物：可反复游玩的战斗循环
  DoD：连续打 10 局不出现卡死/穿墙/无伤害等致命问题；手感通过内部评审
  风险：手感主观。对策——每周固定手感评审会，用可量化参数（后坐力曲线、TTK）对齐。

【M3】关卡与搜刮系统                                    建议周期：4~5 周
  任务：

第 8 章  数据驱动与配置表规划
--------------------------------------------------------------------------------
8.1 原则
    所有数值必须表驱动，代码中禁止出现魔法数字。
    策划改表 -> 自动校验 -> 直接生效，不需要程序介入。

8.2 配置表清单（规划）
    - 武器表：名称、类型、伤害、射速、弹匣、后坐力、扩散、重量、价格
    - 弹药表：口径、穿透、伤害修正
    - 配件表：槽位、属性加成
    - 护甲表：等级、耐久、减伤曲线、覆盖部位
    - 物资表：名称、稀有度、价值、体积、堆叠上限
    - 掉落表：容器类型 -> 稀有度权重 -> 物品池
    - AI 表：血量、精度、视野、反应时间、装备、掉落
    - 地图表：尺寸、出生点、容器分布、撤离点、时限、AI 数量
    - 任务表：类型、条件、奖励
    - 商店表：买入价、卖出价、刷新规则
    - 技能表：效果、等级、消耗
    - 音效/特效映射表

8.3 表管理规范
    - 统一格式与字段命名规范，禁止同义不同名。
    - 提供表结构校验（必填、类型、引用完整性：如掉落表引用的物品必须存在）。
    - 表带版本号，改表需记录变更日志与责任人。
    - 数值改动必须附带预期影响说明（例如：撤离率预估变化）。


第 9 章  性能指标与兼容性标准（H5 专项）
--------------------------------------------------------------------------------
9.1 帧率与稳定性
    - 高配 PC 浏览器：>= 60 FPS
    - 中配 PC / 高端手机浏览器：>= 45 FPS
    - 低配目标机（集显 / 中低端手机）：>= 30 FPS
    - 帧率波动：1% Low 不低于目标值的 70%
    - 连续游玩 30 分钟无内存持续增长（无泄漏）

9.2 加载与体积
    - 首包（首次必要资源）：<= 30 MB，目标 15~25 MB
    - 冷启动到大厅可交互：宽带 <= 8 秒，4G <= 20 秒
    - 进入单局加载（首包已缓存）：<= 6 秒
    - 必须有加载进度反馈，禁止白屏超过 2 秒

9.3 内存
    - 移动端峰值内存 <= 设备可用内存的 60%
    - 场景切换后旧关卡资源必须释放

9.4 兼容性矩阵（需在 M8 逐项实测并记录）
    - 桌面：Chrome / Edge / Firefox / Safari 最新两个大版本
    - 移动：Android Chrome、iOS Safari（最新两个大版本）
    - 分辨率：1366x768 / 1920x1080 / 2560x1440 / 移动竖屏与横屏
    - 设备 DPR：1x / 1.5x / 2x / 3x
    - 明确列出"不支持"的最低版本，并在入口做能力检测与提示

9.5 输入与体验
    - 键鼠：WASD + 鼠标，支持灵敏度调节与按键自定义
    - 触屏：双摇杆 + 自动开火或点击瞄准，按钮可自定义位置与大小
    - 手柄：可选，若支持需在 M2 前决定，避免后期返工

9.6 网络与资源
    - 静态资源走 CDN，带版本号，支持强缓存 + 版本刷新
    - 资源加载失败自动重试（含退避策略）与友好提示
    - 局外数据请求超时与失败降级方案


第 10 章  测试、验收与质量门禁
--------------------------------------------------------------------------------
10.1 测试类型
    - 功能测试：按模块用例逐项验证（每系统一份用例集）
    - 玩法测试：内部试玩，收集"无聊点""挫败点""卡点"
    - 性能测试：每批资源/每次合入后跑基线
    - 兼容性测试：按 9.4 矩阵覆盖
    - 回归测试：每个里程碑结束全量回归
    - 破坏性测试：断线、刷新、切后台、存储写满、资源 404
    - 数值验证：撤离率、单局收益、TTK 是否落在设计区间

10.2 缺陷分级
    S0 阻断：无法进入游戏 / 必崩 / 存档丢失        —— 必须当天修
    S1 严重：核心流程不可完成 / 严重性能问题        —— 本迭代必修
    S2 一般：功能异常但有绕过方式                  —— 排期修复
    S3 轻微：表现问题、文案、体验瑕疵              —— 有余量再修

10.3 质量门禁（未过门禁不得发布/不得进入下一里程碑）
    - 无 S0、无未关闭的 S1
    - 性能指标全部达标
    - 兼容性矩阵全部通过
    - 存档迁移验证通过
    - 回滚方案演练通过

10.4 验收方式
    - 每个里程碑由制作人 + 主程 + 主策 + 测试共同验收并签字
    - 验收结论写入本文件附录 A 交付物清单


第 11 章  团队分工与协作机制
--------------------------------------------------------------------------------
11.1 最小可行团队（6~9 人）
    - 制作人 / 项目经理 1 人：范围、排期、风险、对外
    - 主程 / 技术负责人 1 人：架构、选型、性能、代码评审
    - 客户端程序 1~2 人：系统实现
    - 图形/引擎程序 0~1 人：渲染、优化、特效接入
    - 策划 1~2 人：数值、关卡、AI 行为、任务
    - 3D 美术 1~2 人：模型、场景、动画
    - 特效 / UI 美术 0~1 人（可外包）
    - 音频 外包
    - 测试 1 人（可兼）

11.2 协作节奏
    - 每日站会 15 分钟：昨天做了什么、今天做什么、有什么阻塞
    - 每周：进度同步 + 可玩版本 + 手感/玩法评审
    - 每两周：迭代评审 + 范围与风险复核
    - 每里程碑：验收会 + 文档回写 + 下一阶段计划

11.3 沟通与文档
    - 任务系统统一（看板），每个任务有负责人、预估、验收标准
    - 需求变更必须走变更流程，记录影响并更新排期
    - 禁止口头需求直接开工

11.4 版本管理
    - 主干随时可运行；功能分支开发；里程碑打标签
    - 每日构建（自动构建 + 类型检查 + 静态检查 + 单测）
    - 每个可测版本归档，便于回归与回滚
