## 1. 先用数字确认问题

「太空」不是主观感受，是可量化的：

| 指标 | 当前 M3-1 地图 | 室内 CQB 应有 | 判定 |
|---|---|---|---|
| 内部墙体占比 | **16.6%**（239 / 1444 格） | **18% ~ 30%**（④ 实测 19.7%；上限依据见 §7.1 的修订说明） | 明显不足 |
| 容器密度 | 每 **55** 格一个 | 每 20 ~ 25 格一个 | 明显不足 |
| 最长可射击视线 | 数十米（室外堆场） | 8 ~ 20m | 不符合 CQB |

**根因**：M3-1 我做的是**室外堆场**（几栋楼 + 大片空地），不是室内。
两层的价值不只是"多一层"，而是**在同样 100m×100m 的占地里把可玩面积翻倍**，
同时用楼板把视线切断 —— 这才是电视台那种紧凑感。

## 2. 现状：单层 2.5D 模型的确切假设

现在的几何模型是：**每格一个高度**，语义只有两种。

```js
blocked : Uint8Array(W*H)   // 1 = 从地面到 wallHeight(3.5m) 的实心墙
coverCm : Uint8Array(W*H)   // 厘米；从地面实心到该高度（掩体顶面可站）
```

依赖这个假设的引用点（实测计数）：

| 符号 | 引用数 | 为什么装不下两层 |
|---|---|---|
| `groundHeightAt` | 11 | 只返回"一个高度"，没有"在第几层"的概念 |
| `coverCm` | 12 | **`Uint8` 最大只有 2.55m**，表达不了 4m 的楼板 |
| `resolveCircle` | 8 | 单一 `feetY` 对单一高度，没有"头顶还有楼板" |
| `raycastWall` | 7 | DDA 假设每格只有一层墙，无法表达"穿过挑空打中对面" |
| `pathBlocked` | 7 | **`Uint8Array(W*H)` 纯二维**，A* 在 `W*H` 上跑 |
| `level.free` | 8 | 扁平列表，没有层 |
| `spawnable` | 3 | 同上 |

最要命的一处：`ai.js:166` 是

```js
ai.position.y = level.groundHeightAt(ai.position.x, ai.position.z);
```

**AI 被直接吸到地面高度** —— 它没有"我在二层"这个状态，所以 AI 跨层寻路
等于要重做寻路的数据结构，不是加个分支就行。

## 3. 目标数据模型

### 3.1 从「一个高度」改为「一组实心跨度」

每格不再只有一个高度，而是一组**竖直实心跨度**（按 y 升序、互不重叠）：

```
一层墙        span [0.0, 3.5]  kind=wall
一层掩体      span [0.0, 1.05] kind=cover
二层楼板      span [3.6, 3.9]  kind=slab      ← 楼板下方是通的（可在一层走）
二层墙        span [3.9, 7.4]  kind=wall
楼梯（斜坡）  span [3.6→7.2]   kind=ramp      ← 起止高度 + 方向
```

这个模型**同时泛化了 `blocked` 与 `coverCm`**：墙就是一个从 0 到 3.5 的跨度，
掩体就是一个从 0 到 1.05 的跨度。因此它是**推广**而不是另起一套，
现有语义可以无损表达（迁移风险低）。

**存储**：用 CSR 式扁平数组而不是"每格一个 JS 数组"，避免对象churn 与 GC 抖动：

```
spanY0    : Float32Array    // 跨度底
spanY1    : Float32Array    // 跨度顶
spanKind  : Uint8Array      // wall | slab | cover | ramp
spanDir   : Uint8Array      // ramp 用：0=+x 1=-x 2=+z 3=-z
spanStart : Int32Array(W*H+1)  // 每格的跨度区间 [spanStart[i], spanStart[i+1])
```

1600 格 × 2 层 × 约 2 个跨度 ≈ 6400 个跨度。内存约 `6400×(4+4+1+1)` ≈ 64KB —— 可忽略。

### 3.2 关键算法改动

| 函数 | 新签名 | 做法 |
|---|---|---|
| `groundHeightAt` | `(x, z, y)` | 取"顶面不高于 `y+ε`"的**最高**跨度的顶面 |
| `blockingSpanAt` | `(cx, cz, feetY, height)` | 与实体竖直区间 `[feetY, feetY+height]` 相交、且顶面高出脚底超过 `stepHeight` 的跨度 |
| `resolveCircle` | `(pos, radius, feetY, height, stepHeight)` | 圆 vs 每格每个跨度的 AABB（3D） |
| `raycastWall` | 不变签名 | DDA 进入某格后，对该格**每个跨度**求"格子内 t 区间 ∩ y 区间"的交集，取最小合法 t |
| `hasLineOfSight` | 不变 | 自动获得正确的跨层语义 |

`raycastWall` 的推广是这套方案的核心：它让**挑空区可以跨层对射**、
**楼板区挡子弹**这两件事由同一段代码自然得出，而不是靠特判。

### 3.3 ★ 楼梯为什么必须是斜坡，不能是台阶

这一条我算过，它决定了要不要新增一种跨度类型，所以单独说明。

现有台阶吸附靠 `stepHeight = 0.60m`。若用离散台阶做楼梯：

```
层高 3.6m ÷ 0.60m/级 = 6 级，每级占 1 格 = 6 格 = 15m 长的楼梯
```

**15 米长的楼梯**显然不能用（电视台的楼梯最多 3~4 格）。

若用真实级高（0.18m/级），则 3.6 ÷ 0.18 = **20 级** —— 更不可能，
而且每级都远小于 `stepHeight`，等价于一条斜坡。

**结论**：楼梯必须实现为**连续斜坡**，不是离散台阶。坡度取 28°（常见楼梯），
则一层楼梯的水平投影 = `3.6 / tan(28°) ≈ 6.8m ≈ 2.7 格` —— **3 格左右**，符合实际。

斜坡是本次**唯一新增的跨度类型**。它带来两个好处：
- 楼梯只占 3 格而不是 15 格；
- 玩家与 AI 走上去是**连续**的，不会出现"一级一级弹跳"的观感。

代价：`groundHeightAt` 在 ramp 格上要做线性插值，`resolveCircle` 要允许"坡面不阻挡"。
这两处都是局部改动，不影响其他部分。

### 3.4 寻路：分层网格 + 楼梯链接

导航图从 `W*H` 扩为 `floorCount * W * H`：

- **节点** = `floor * W*H + cell`
- **同层边** = 现有四邻接，但阻挡判定用**该层的可走空间**（不是"格子里有没有东西"）
- **跨层边** = 楼梯格在相邻两层之间连一条边（代价 = 坡长）

节点数 2 × 1600 = 3200 —— 对 A* 完全无压力。
现有寻路预算机制（`pathBudget.maxQueriesPerFrame` / `maxMsPerFrame`，C-1/C-2）**不用改**。

**重要简化**：因为楼梯是斜坡（连续表面）而不是台阶，
`followPath` 只需要让 `y` 跟随 `groundHeightAt(x, z, y)` 插值即可 ——
**不需要为"爬楼梯"写任何专门代码**。

## 5. 设计：电视台式两层平面（评审用草图）

**占地仍为 40×40 格（100m×100m）**，靠楼板把可用面积翻倍并切断视线。

### 5.1 分区（每层）

```
一层（入口层，风险较低，价值中等）
  ① 安检大厅      —— 出生区。金属探测门 + 行李转盘（低掩体密集）
  ② 办公区        —— 工位隔断（低掩体）+ 文件柜（民用箱扎堆）
  ③ 服务器机房     —— 冷通道机柜（高掩体，挡子弹）+ 保险箱
  ④ 货运通道      —— 卸货平台 + 卷帘门，南北贯通
  ⑤ 地下车库入口   —— 死角，高价值但也最容易被堵

二层（高价值层，风险高）
  ⑥ 演播厅        —— 挑空中庭（可俯视一层大厅，跨层对射）
  ⑦ 控制室        —— 玻璃隔断（可视不可穿）+ 保险箱
  ⑧ 办公走廊      —— 长直走廊（最危险，无掩体）
  ⑨ 天台出口      —— 通往东北撤离点
```

### 5.2 垂直连接（这是电视台设计的灵魂）

| 连接 | 类型 | 设计意图 |
|---|---|---|
| 主楼梯 A | 双向斜坡楼梯 | 大厅 → 二层演播厅。**最长、最暴露**，是正面通道 |
| 主楼梯 B | 双向斜坡楼梯 | 货运通道 → 二层走廊。绕远但安全 |
| 电梯井 | **单向：只能跳下，上不去** | 二层 → 一层车库。制造**单向垂直动线** |
| 挑空中庭 | 完全贯通 | 演播厅可俯视大厅 —— 控制二层等于控制一层 |

**「可跳下不可上」是电视台最关键的一条设计**：它让二层成为
"上得去、下得快"的高风险高收益区，玩家必须在上二层前想清楚退路。
M3-1 的动线教训在这里同样适用 —— 我会用**帕累托支配检查**
（每条路线都必须有存在理由）来校验垂直动线，而不是只看"能不能走通"。

### 5.3 与 M3-1 的关系（不浪费已有工作）

M3-1 的**平面布局思想**（价值梯度：出生区→资源区→交战区；三条取舍不同的动线）
可以**直接复用为"一层的平面"**。两层的设计本质是：
**把 M3-1 的"外围资源区"上移到二层，让"上楼"本身成为一种动线选择。**

## 6. 风险登记

| # | 风险 | 后果 | 对策 |
|---|---|---|---|
| R1 | AI 跨层寻路错乱（原地打转/穿模） | 玩法直接崩 | 分层网格 + 楼梯边；新增断言"一层任一点到二层任一点必须能寻到路径，且路径层序列必须包含楼梯" |
| R2 | 子弹穿透楼板 | 掩体对抗的根基被破坏 | 跨度区间求交；断言"从一层正上方射击必被楼板挡住；在挑空区则不挡" |
| R3 | 玩家掉层后卡在几何里 | 直接是 S1 缺陷 | `resolveCircle` 用实体竖直区间；断言"从二层边缘走落，落地后不在任何实心跨度内" |
| R4 | **`groundHeightAt` 的层歧义被静默吞掉** | 最危险的一条：同一 x/z 在两层都可通行时，不传 y 就会取错层，表现为"莫名传送/卡住" | **直接删掉不传 y 的旧签名，不留默认值** —— 有默认值就等于允许忘记传。靠编译/运行时报错逼出所有调用点 |
| R5 | 性能回退（射线成本翻倍） | 违反 M0 性能基线 | 先实测 `raycastWall` 单次耗时；若超预算，对"只有一个跨度的格"加快速路径（多数格属于此类） |
| R6 | 大量既有断言失效 | 套件不可信 | 先改 level 接口并跑全量套件，让失败**暴露所有调用点**；再逐组修断言，禁止为了通过而放宽 |
| R7 | 地图表格式变更破坏现有工具链 | 地图图/校验脚本失效 | `render-map.mjs` 同步支持分层；旧表迁移脚本一次性转换 |
| R8 | 范围蔓延（电梯/可动楼梯/多层掩体高度差/电梯动画） | 无限膨胀 | 本方案明确**不做**（见 §8） |

## 7. 验收标准（可测量，不含"感觉"）

1. **密度**：单层内部墙体占比 **18% ~ 30%**；容器密度 ≤ 每 25 格一个。
   > 这条指标改过两次，都留在文档里以便追溯：
   > 初版拍 **35 ~ 45%**；④ 第一次实施做到 33.4%，**试玩否决**（"一楼墙数量太多"——
   > 观感是 5×5 的格子迷宫）；第二次改成 9 格隔墙周期 + 去掉满地结构柱，
   > 实测 **19.7%**，观感是 8×8 大房间 + 走廊。
   > 所以上限 30% 是有实测依据的（33.4% 已被否决），不是又拍了一个数。
2. **两层都可用**：二层可通行面积占单层的 40% ~ 60%。
3. **连通性**：一层出生点 → 二层每一个资源点，A* 必须给出路径（脚本断言，遍历全部点对抽样）。
4. **跨层射击**：
   - 挑空区：一层 ↔ 二层可互相命中（断言）；
   - 楼板区：不可命中（断言）。
5. **落地正确性**：从二层边缘走落，落地高度必须等于一层地面且不在实心跨度内（断言）。
6. **AI 不迷路**：让 AI 追击位于另一层的玩家，必须经由楼梯抵达（断言路径层序列），且不出现穿模。
7. **性能**：同场景同 AI 数下，帧率不低于改动前的 90%；单帧寻路仍 ≤ 2ms（C-2）。
8. **套件**：端到端与单测全绿；新增分层不变量 ≥ 12 条；每条新规则都要有**注入自检**
   （沿用本项目惯例：从不失败的检查等于没有检查）。

## 8. 本方案明确**不做**的（防范围蔓延）

- 电梯（可动平台）、可开关的门、可破坏楼板
- 三层及以上
- 二层掩体的"高度差"（例如栏杆可蹲可站）—— 留到 M6 内容扩充
- 二层独立的地图美术表现（M7 换皮统一处理）
- 移动端适配（本项目目标为 PC 浏览器）

## 9. 工作量与排期建议

**我的估算是"与 M2 战斗手感成型同量级"的中大型任务**，理由是：
核心几何（level）、寻路（navgrid）、AI 跟随三处都要改，且这三处是**相互耦合**的
（几何变了寻路要变，寻路变了 AI 要变，AI 变了要重新验证行为）。

但**我必须说清楚：这个估算是基于改动面计数的推断，不是实测。**
我过去在"低估回归面"上踩过坑（M2 的台阶吸附改动引出了"跳跃完全坏掉"和"落地缓冲恒为 0"
两个我自己引入的缺陷）。因此我建议**分两步交付、每步都可玩**：

| 步骤 | 内容 | 交付后能玩到什么 |
|---|---|---|
| **M3-1b-1** | 分层几何 + 分层碰撞/射线（含楼板、斜坡）；地图表格式；单层回归全绿 | 仍是一层，但几何模型已换成跨度制（**行为必须与现在完全一致**，这是它的验收标准） |
| **M3-1b-2** | 分层寻路 + AI 竖直跟随 + 二层地图落地 | 真正可玩的电视台式两层图 |

**分两步的价值**：第一步的验收标准是"行为不变" —— 这是一个**强不变量**，
能可靠地证明几何改造没有引入回归。若把它和二层地图混在一起做，
一旦出问题，就分不清是"几何改造错了"还是"新地图设计错了"。

5. **「电梯井可跳下不可上」** 是否保留？它是电视台式设计的关键，

   撤离点**至少一个在二层**（否则二层只有风险没有回报出口）。

### 12.2 发现的旧缺陷：**擦过低掩体上方即可穿墙**（严重）

黄金基准比对暴露出 922 条 `raycastWall` 分歧，方向**全部是"旧实现未命中、新实现命中"**
（另有 290 条 `hasLineOfSight` 同源分歧：旧说"视线通畅"、新说"被挡"）。

**根因** —— 旧 `raycastWall` 里有这条捷径：

```js
if (y > h) { if (dy >= 0) return Infinity; ... }
//          ^^ "在这格阻挡体上方且不下降 → 不可能再撞到任何东西"
```

它**假设所有阻挡体一样高**。而本项目里掩体 0.45m / 1.05m、墙 3.5m ——
"在低掩体上方"完全不蕴含"在墙上方"。于是：

> **只要射线先擦过一格低掩体上方，它就会穿过后面所有的墙。**

玩家视角的表现：**站在矮墙后开枪，子弹穿墙打死掩体后面的人。**

**最小复现**（已固化为单测断言）：
地图上 (20,29) 是空地、(21,29) 是 0.45m 低掩体、(27,29) 是墙。
从 (20,29) 以眼高 1.65m 平射，墙面距离应为 **38.750m**：
旧实现返回**未命中（穿墙）**，新实现 38.750m ✓。

**为什么 M1 的"隔墙打不中"用例没抓到它**：那条用例的射线路径上**没有低掩体**，
因此从未进入这条缺陷分支。它只在"低掩体 + 后方有墙"的几何组合下出现 ——
是靠 922 条随机采样射线才暴露的。

**归因方法（不是"我觉得那是修 bug"）**：校验器内置了一份旧算法，
对每条分歧都要求**证明旧算法确实走了那条缺陷路径**；
凡无法归因的分歧一律算回归并判失败。本次：已归因 1212 条，无法归因 0 条。

**新增回归防线**（`tools/unit-tests.mjs`）：断言"空地起射 → 擦过一格低掩体 → 必须被墙挡住"，
外加一条反向对照（抬到墙顶以上则确实不该命中，防止"一律命中"式的假通过）。
该断言做过**注入自检**：把旧缺陷放回去 → 断言失败；撤销 → 全绿。

> **顺带一条教训**：这条回归断言我**第一版写成了空的** ——
> 从掩体格中心起射，射线根本没经过掩体，因此注入缺陷后仍然 123/123 全绿。
> 是注入自检把它抓出来的。**回归测试必须复现触发条件，而不只是复现"结果看起来不对"。**

### 12.3 实施中的其他发现

- **跨度必须合并**：边界墙在四个角会被压入两次（x 循环一次、z 循环一次）。
  旧实现用 `blocked[i] = 1` 天然幂等，跨度列表则必须显式合并 ——
  否则"同一格有两条 `[0,3.5]` 的墙"会让后续区间运算重复计数。
  这个错误在首次运行时就被跨度表的构建期断言拦下。
- **不要把正确算法"顺手改优雅"**：`raycastGroundFull` 我一度改成"与跨度求交"的更优雅写法，
  结果引入 **9 条真实回归**（原本能命中掩体顶面的射线变成打到地面）。
  原因是旧算法里 `groundHeightAt(gx,gz) === g` 这条校验允许交点落在**相邻同高掩体格**上，
  而我换成"交点必须仍在采样格内"后把它排除了 —— 一个看起来更严格的判据反而弄坏了正确行为。
  已改回逐字保留旧算法、只把"取掩体高度"换成从跨度表派生。
  **在有黄金基准的前提下，先保行为，再谈优雅。**

## 13. M3-1b-2 ② 实施结果：分层寻路

### 13.1 交付内容

节点空间从 `W*H` 扩为 `floorCount * W*H`（**节点 = floor*W*H + cell**），
并给每格每层加一个**落脚高度区间** `[lo, hi]`；格边除了"目标格不阻挡"之外，
还必须满足"两格区间相距 ≤ stepHeight"。楼梯的**坡顶格**上连一条跨层边。

三个文件：

| 文件 | 改了什么 |
|---|---|
| `src/level/level.js` | 构建分层寻路数据（每层可走性、落脚高度区间、坡顶跨层边），以 `level.nav` 导出 |
| `src/core/navgrid.js` | `createNavGrid` 泛化为 `createLayeredNavGrid`；A* 支持分层节点、高度差门槛、跨层边 |
| `src/main.js` | 接线改用 `createLayeredNavGrid(level.nav)` |

### 13.2 两个关键设计决定（都与方案 §3.4 的原文不同，理由在此）

**① 跨层边的代价是 0，不是"坡长"。**
方案 §3.4 写的是"代价 = 坡长"。实测建模后发现那是**重复计数**：
跨层边的两端是**同一格、同一世界坐标**，几何位移为 0；坡道的水平长度
已经由同层的坡格序列（几步同层边）计入了。再加一次坡长会让启发式高估、
A* 不再最优。竖直分量在二维网格 A* 里本来就被忽略（同层边的代价也只用水平距离），
单独给跨层加进来反而与同层边语义不一致。

**② 用"落脚高度区间"而不是"一个高度"，是为了让高度差门槛不切断坡道。**
若普通格与坡格都只记一个高度，那么"相邻格高差 ≤ stepHeight"这条规则会：
- 正确剪掉「一层地面 → 坡顶格」（高差 2.4m，不剪就会让 `surfaceAt`
  把脚底从 0 一把抬到 2.4m，表现为**瞬移上坡**）；
- 但同时把**坡道自己**切断（层高 3.6m ÷ 3 格 = 单格落差 1.2m > stepHeight 0.6m）。
坡是**连续面**，所以坡格记的是坡面在该格内的**区间**；相邻坡格区间首尾相接、
差值为 0，天然连通。一条规则同时表达"低掩体可迈上""坡道连续可走""不能瞬移上坡"三件事，
不需要为楼梯写任何特例。

### 14.2 竖直跟随分三种情况（这一步的核心）

旧写法是一句 `ai.position.y = level.surfaceAt(...)`，它隐含假设
「地面高度连续、落差不超过 stepHeight」。单层世界成立（最大落差就是低掩体的 0.45m），
**两层世界不成立**。新的 `followGround` 分三种：

| 情况 | 处理 | 理由 |
|---|---|---|
| 落差 ≤ `stepHeight` | 直接贴合 | 迈下台阶。**单层地图 100% 走这条**，因此与旧行为逐字相同 |
| 斜坡格 | 直接贴合 | 坡面是按世界坐标插值的**连续量**，它的"落差"不是台阶；用台阶判据切它会把下楼变成抖动 |
| 其余（真掉层） | 按 `cfg.player.gravity` 连续下落 | 从二层走出楼板边缘时 `surfaceAt` 会直接返回一层地面 0，瞬移 3.6m 就是穿模 |

"单层 100% 走第一条"不是抽样观察，而是一条**遍历断言**：
对地图上所有相邻可走格对，算出按真实过程行走时的落差，断言它恒 ≤ `stepHeight`。
只要成立，下落分支在单层地图上就是死代码。

### 14.4 ★ 过程中发现并修复的既有缺陷：**AI 在非巡逻状态下无法沿路径移动**

这是本步最重要的发现，严重程度高于 ③ 本身。

**现象**：AI 一旦进入 ALERT / COMBAT / SEARCH 且需要寻路靠近，就会**原地抖动**。
实测（工业地图、固定目标、300 帧）：净位移 **0.024m**，`pathIdx` 在 0 与 1 之间来回。

**根因**：

```js
const r = scheduler.takeResult(ai.id);
if (r) { ai.path = ...; ai.pathIdx = 0; ai.pendingGoalCell = null; }
```

`takeResult` 每次拿到结果都把 `pathIdx` **归零**，同时把 `pendingGoalCell` 清空 ——
而 `pendingGoalCell` 正是 `requestPath` 的去重判据。于是 ALERT/COMBAT/SEARCH
（这几个状态**每帧**都会用同一目标调用 `requestPath`）每帧重新请求，结果每两帧回来一次，
`pathIdx` 就每两帧被归零。`followPath` 一次只处理一个节点，
所以 AI 永远在"消费第一格 → 归零 → 再消费第一格"之间循环。

**为什么 M2 没有抓到它**：
- "AI 会移动"测的是**巡逻**状态。巡逻只在"没有路径"时才请求，不受影响 —— 一直是绿的。
- "被攻击的 AI 会主动逼近（≥3m）"在测试里跑的是 **COMBAT + 看得见玩家 + 中等距离**。
  那个分支按设计**不请求路径**，于是走的是 `moveToward` 直接逼近 —— 也一直是绿的。
- 真正坏掉的是**"看不见、需要绕行"**的那条路：只听到枪声、失去视线、被压制后转移。
  这条路上 AI 站着抖，玩家看到的是"它知道我在哪，但就是不过来"。

**这不是本步引入的（已实测确认）**：把工作树 stash 回 ① 的状态，用同一份诊断脚本跑，
新旧输出**一字不差**（`moved: 0.024`、`pathIdxMax: 1`、`pathLen: 43`）。

**修复**（3 处，都在 ai.js 内）：给 AI 记录"当前路径的目标节点 `pathGoal`"与
"最后一次请求的目标 `lastRequestedGoal`"，只有**目标真的变了**才重置 `pathIdx`；
`requestPath` 也据此多一条去重判据（正在走这条路径且目标未变就不重算）。
修复后同一诊断脚本位移 0.024m → **7.05m**。

**影响面（必须让用户知道）**：这改变了 M2 已验收的 AI 行为 —— 它让 AI 在
"需要绕行"的情况下真的会绕行，也就是**显著变强**。单测与端到端在修复后全绿
（10 局数据与修复前完全一致：开火 14 / 命中 3 / 生命 89），但那是自动化场景；
实际难度感受需要试玩确认。

### 14.5 发现但未处理的问题

1. **`ai.lastKnownPos` 的 y 只有"看到"和"被击中"时才有**。`hearGunshot` 虽然加了可选 y，
   但听觉在真实玩法里只传得出水平位置 —— 也就是说"只听到楼上有人开枪"时，
   AI 仍按自己所在层去找。这与听觉本身的语义一致，但值得在 ④ 试玩时观察是否需要加强。

### 15.2 ★ 几何模型强加给地图设计的三条硬约束

这三条是实施过程中被**实测**逼出来的，不是设计偏好。记在这里，因为后续任何两层内容扩充都会撞上它们。

> **⚠️ 修订（第三轮"楼板压墙"之后）**：下面的 **①③ 两条已经不成立了**。
> 它们都源于同一个几何限制——"楼板与墙重叠会报错"，而那条限制是按制作人裁定改掉的。
> 现在重叠的两条跨度会合并成一条贯通实体（kind 取更实心的 WALL），
> "这一层有没有地板"改由**顶面高度**判定。
> 结果：一层墙顶照样是二层的楼面，二期是完整平面，**两层可以各有一套隔墙**。
> **只有 ② 仍然有效**（门洞仍然是跨层通道的语义来源，虽然不再是"桥"）。
> 保留原文是为了让"为什么会有这三条"可追溯——它们是同一根约束的三个侧面。

**① 楼板不能压在一层的墙格上。**（**已解除**）
楼板 `[3.3, 3.6]` 与一层墙 `[0, 3.5]` 在几何上重叠。所以"一层墙格的投影"在二层**必然没有楼板**，也就是**洞**。
推论：**二层的可走区天然是"一层可走区的子集"**，二层的格局变化只能靠"哪里铺楼板"（挑空、电梯井）来表达。

**② 一层的门洞就是二层的桥，所以每个房间都必须有自己的门。**
既然一层墙格在二层是洞，二层要横跨这些洞就只能走"一层门洞所在的那一格"。
第一版我把门洞固定成 3 个位置（8/20/32），结果靠边的房间四面无门 —— 二层连通块只剩 **207/647**。
改成"每一段的中心各开一个门"之后：一层 **934/939**、二层 **910/912**。

**③ 二层不能再加自己的隔墙。**（**已解除**）
第一版给二层配了一套错开半个网格的隔墙，结果二层的横墙正好压在一层门洞形成的 1 格宽"桥"上，**把桥全堵死**（二层连通块 43/589）。
二次尝试改成与一层对齐也不行 —— 那不是"多一层布局"，只是把同一套格局画两遍。
最终**二层不设任何自己的墙**：一层墙的投影已经是它的洞网。

### 15.4 三处偏离与它们的裁定结果

**① 墙体占比 —— 改过两次，最终 19.7%。**

- 初版目标 35%，第一轮做到 33.4%，**试玩否决**（"一楼墙数量太多"）。
- 第二轮把隔墙周期从 6 格改成 9 格（房间 8×8）、并**去掉满地 2×2 结构柱**，实测 **19.7%**。
- §7.1 的目标相应改成 **18% ~ 30%**：下限保证"不空"，上限 30% 有实测依据（33.4% 已被否决）。
- **教训**：我第一轮是为了"凑 §7.1 的 35%"而加密的，甚至加了满地结构柱 —— 那不是设计，
  **是拿地图去迁就一个我自己拍出来的指标**。指标应该是设计的结果，不是设计的目标。

**② 容器预算与搜刮耗时门禁的冲突 —— 已裁定按"提高单局时限"解决。**

§7.1 要求容器密度 ≤ 每 25 格一个 → 87 个容器；
而 `tools/validate-loot-tables.mjs` 有一条门禁：**"全部容器搜完的耗时 ≤ 单局时限的 40%"**。
87 个容器全部搜完 = **296s**，在原来的 240s 时限下是 **123%** → 门禁失败。

我原本建议改门禁口径（"全部容器" → "装得下的容器"），但**制作人裁定提高时限**：

| | 时限 | 全部搜完占比 | 门禁 |
|---|---|---|---|
| 改前 | 240s | 123% | 失败 |
| 第一次改后 | 660s | 77.7%（当时 74 个容器 → 251s） | 未定稿 |
| **第二次改后** | **780s（13 分钟）** | **37.9%** | 通过 |

> 这里改了两次，原因是三者是一根**链子**，必须一起算：
> **墙变少 → 可玩面积变大 → 容器按密度自动变多 → 所需时限变长**。
> 第二轮把墙从 33.4% 降到 19.7%，可玩面积从 1851 涨到 2170 格，容器随之从 74 涨到 87 个。
> 时限写在 `tunables.raid.timeLimitMs`（唯一真值），并顺手修掉了一处硬编码：
> `validate-loot-tables.mjs` 原本自己写死 `240000`，现在改为从 tunables 读。

### 15.6 ★ 第一轮试玩反馈与修复（这段是本次迭代最有价值的部分）

制作人实际看了第一版地图后给出两条反馈，**两条都是我的错**：

**反馈一：「楼梯无法抵达二楼，被地板塞满了」—— 功能性缺陷。**

根因：楼梯井的**全部 12 个格**都被铺了二层楼板。

我在生成地图时，楼板的排除列表里有"一层墙格、电梯井、挑空"，**唯独漏了楼梯井**。
后果不是"看起来怪"，而是**真的上不去**：
玩家在坡道上时身体竖直区间 `[脚底, 脚底+1.8]` 与楼板 `[3.3,3.6]` 相交，
被 `resolveCircle` 顶住。

★ **最值得记的是它为什么没被测试挡住**：
`A*` **仍然会给出一条经过楼梯的路径** —— 分层寻路只看"格可走性 + 落脚高度门槛"，
而坡格在两层都有落脚面，所以在它眼里楼梯是通的。
**"路径存在"与"人上得去"是两件事。**

修复分两层：
1. 生成规则：楼梯井（ramp 覆盖的每一格）在二层不铺楼板。
2. **新增 6 条断言**，其中两条是真正的防线：
   - 「楼梯井的每一格都没有被上层楼板盖住」—— 直接、廉价，能报出是哪一格堵的；
   - 「沿该路径前进时不会被几何挡住」—— 沿 A* 路径**逐采样点**递推脚底高度并跑
     `resolveCircle`，检查是否被推开。**只看格中心会漏掉"两格之间被挡住"**，
     所以相邻格连线上也采样。

**注入自检**（把楼板盖回楼梯井 → 重新生成 → 跑单测）：
两条断言都以正确方式失败，第二条报的是
`格 (13,30) 附近 (13.5,30.8) 被推开 0.22m` —— **精确复现了玩家被顶住上不去的那 0.22m**。

**反馈二：「一楼墙数量太多」—— 设计问题。**

第一轮为了凑 §7.1 那 35% 的墙体占比，我把隔墙做成 6 格周期（房间 5×5），
还加了满地 2×2 结构柱。观感是格子迷宫。

**根因是我拿地图去迁就一个自己拍出来的指标。**
指标应该是设计的结果，不是设计的目标 —— 这一条比任何技术细节都值得记。

修复：隔墙周期改成 9 格（房间 8×8）、去掉结构柱、门洞 2 格宽，
并保留 6 个 4×4 设备间/卫生间提供层次。实测墙体占比 **33.4% → 19.7%**。

同时把生成器**保留为正式工具** `tools/gen-map-tv-station.mjs`（此前是一次性的、用完就删）——
密度、房间尺寸、门洞宽度现在都是文件顶部的几个参数，改动不再需要重写几百个矩形。

### 15.7 第三轮：楼板压墙（几何模型改动）

第一轮留下的"二层地面到处是一格宽的沟"是**几何模型**造成的，不是地图数据问题：
楼板 `[3.3,3.6]` 与一层墙 `[0,3.5]` 有体积交叠，config 直接报错，
于是地图只能让一层墙格在二层不铺楼板 —— 那些格就成了洞。
连带后果是二层**不能有自己的隔墙**：一加墙就正好压在那些 1 格宽的通道上（实测连通块 43/589）。

制作人裁定：**改几何模型允许楼板压墙**。改动落在三处：

| 位置 | 改动 |
|---|---|
| `level.js` 跨度合并 | 只有**真正重叠**才合并（相接的一律保留两条，否则会丢掉"楼板 + 它上面的掩体"这种组合）；重叠时 kind 取**更实心**的（wall > slab > cover），于是一层墙 + 二层楼板合成 `[0,3.6]` 的墙 |
| `level.js` nav 构建 | "这一层有没有地板"从「`kind === SLAB` 且顶面 == 该层标高」改为**只看顶面高度**。几何上这个判据本来就该这么写 —— 与它叫墙还是叫楼板无关 |
| `config/index.js` | 删掉"楼板与墙不得重叠"的报错（保留"掩体不得埋进墙里"） |

**收益**（都有断言钉住）：
- 二层成为**完整平面**：楼板 1364 格，一层墙格在二层可走；
- 二层**可以有自己的隔墙**了：新增 257 格，两层的可行走区域因此确实不同；
- 一层的门洞不再承担"跨层桥梁"的角色，地图设计少了一层隐性约束。

**注入自检**：把地板判据退回"只看 kind"→ 2 条断言失败：
「★ 楼板压墙生效：一层墙格在二层是可走的」（`blocked=1`）与
「一层出生点 → 二层天台门有路径」（`len=0`，二层被切碎）。恢复后 183/183。

**顺带修掉的一个夹具缺陷（值得单记）**：
`placeNextToWall` 用 `isBlockedCell` 判断"右边是不是墙"。而 `isBlockedCell` 是**单层语义的快照**
（"这格有没有墙跨度"），在两层地图上它会把**二层**的墙也算进来 ——
实测它选中了格 (8,1)，那一格的跨度是 `[楼板 3.3~3.6] + [墙 3.6~7.1]`，**一层根本没有墙**。
射线从眼高打过去什么也打不到，探头自然不会被评为"被墙收回"，
断言报"隐含横向速度 0 m/s"，看起来像功能坏了。

改法是让夹具**直接射一次**（"从眼高朝右、在探头可及范围内能不能打到东西"就是它要的判据），
顺带自动排除高掩体（1.05m 低于眼高 1.65m）。修复后该断言报 **4.40 m/s**，正是限速上限
（`leanClampRate × leanOffset = 8 × 0.55`）—— 说明裁剪真的触发了。

同类问题还有一处：AI "主动逼近"的观察窗口原为 4.8s。这张图可玩面积是单层的 1.5 倍、隔墙更密，
AI 从 12m 外过来常要绕路，4.8s 内直线距离只缩短 2.5m（阈值 3m）——
它**确实在靠近**，只是窗口太短。窗口放宽到 9.6s，**判据本身没动**。

### 15.5 剩余工作（未做）

- **动线（`routes`）为空**：新地图还没画动线图。`render-map` 的"帕累托支配"检查因此没有实际内容。
  方案 §5 要求"用帕累托支配检查校验垂直动线"，这需要在 ④ 之后补一轮动线设计。
- **AI 出生仍在第 0 层**：`aiManager` 的 `zoneOfCell` 只匹配第 0 层分区（AI 出生格是单层的格坐标）。
  二层靠 ③ 的跨层追击覆盖。若要让部分 AI 开局就在二层，需要让 `spawnCell` 带层号。

  没有楼梯 → A* 找不到上去的路），但还没有一条断言把它钉住。

  "两层地图"的有楼梯贯通、跨层可达、掉层连续、分层阻挡、楼板压墙等，离 §7 列的 8 类验收还有距离。
